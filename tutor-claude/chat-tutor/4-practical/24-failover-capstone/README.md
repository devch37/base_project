# 24. 서버 장애 후 재연결과 화면 재동기화 — 그리고 캡스톤

## 이 장의 목표
- 서버가 죽거나 재시작될 때 **고객·상담사·서버·공유 저장소** 각각에서 무슨 일이 일어나는지 시간 순서로 설명할 수 있다.
- 장애 유형별(정상 종료, 강제 종료, 네트워크 단절, 토큰 만료, 강제 퇴장 …) 기대 동작을 표로 말하고 재현할 수 있다.
- 최종 프로젝트 전체를 처음부터 끝까지 설명할 수 있다 (캡스톤).

## 1. 서버 A 가 갑자기 죽었을 때 (kill -9)

`web/e2e/cluster.e2e.ts` 가 실제로 하는 일 (고객→A, 상담사→B):
```
t=0   A 프로세스 SIGKILL — 정리 코드(@PreDestroy, 연결 close)가 돌 기회 없음
      고객 브라우저: TCP 끊김 감지 → close 1006
      transport.ts: 백오프(jitter) 후 "다음 주소"(urls[1] = B)로 재연결
      getToken('reconnect') → 고객사 서버가 새 토큰 (고객사 서버도 A 가 죽었으면 B 로 — chatApi 의 다음 서버)
t≈1s  고객 → B 로 CONNECT → 재구독 → onConnected → resnapshot() → 새 epoch 스냅샷
      상담사(B): 새 epoch 스냅샷 수신 → 복제본 전체 재구성 → 이후 변경분 정상
      방 정보(IMap): A 가 가진 파티션은 B 의 **백업**으로 승격 → 방·배정·동의 그대로
t≈10s Hazelcast: A 를 멤버에서 제거 (max.no.heartbeat 10s)
t≈TTL A 가 써 둔 presence 항목: 갱신이 멈췄으므로 TTL 뒤 자동 삭제 → presence.nodes = [B]
```
e2e 실측: 재연결 후 입력 동기화·DOM 변경 반영·A 의 presence 소멸 모두 통과.

## 2. 장애 유형별 기대 동작

| 상황 | 고객/상담사 close code | SDK 동작 | 서버 쪽 | 재현 방법 |
|---|---|---|---|---|
| 서버 정상 종료 (SIGTERM, graceful) | 1001 | 백오프 → 다음 서버 | `server.shutdown=graceful`: 진행 중 요청 마무리 후 종료 | 서버 터미널 Ctrl+C |
| 서버 강제 종료 (kill -9) | 1006 | 〃 | 정리 없음 → TTL 이 청소 | `kill -9 <pid>` |
| 서버가 연결만 끊음 (실습 API) | 1001 | 〃 (같은 서버로 재연결 가능) | — | `POST /internal/admin/drop-connections` |
| 고객 네트워크 단절 | 1006 (heartbeat 타임아웃 후) | 복구 시 재연결 + 새 스냅샷 | heartbeat 로 세션 정리 → presence 퇴장 | 개발자도구 Network → Offline |
| 토큰 만료 | 4001 | 새 토큰 → **즉시** 재연결 | `ExpiredSessionSweeper` | `?ttl=40` 으로 고객 페이지 열고 갱신 끄기* |
| 배정 해제 / 강제 퇴장 | 4003 | **재연결 안 함** (`stopped`) | 모든 노드에 kick 방송 | 상담사 콘솔 대신 `curl -X POST …/internal/users/agent-1/kick -H 'X-Api-Key: dev-acme-key'` |
| 권한 없는 주소 접근 | 1008 | 재연결 안 함 | 인터셉터가 소켓 종료 | (버그·변조 클라이언트) |
| 고객사 백엔드 다운 | (연결은 유지) | 토큰 갱신 실패 → 다음 주기 재시도, 재연결 시 백오프 | — | `npm run tenant` 종료 |
| 큰 메시지 한도 초과 | 1009 | 재연결 → 같은 큰 스냅샷 → 반복 (**설정 불일치 버그**) | — | 18장 도전 과제 |

\* 고객 페이지는 `ttl` 의 절반마다 토큰을 갱신한다(`tokenRefreshMs`). 만료를 보려면 `customer/main.ts` 의 `tokenRefreshMs` 를 0 으로 바꿔 보자.

## 3. 재동기화가 "공짜로" 되는 이유 — 설계 복습

1. 고객 SDK 는 **끊긴 동안 프레임을 버린다** (쌓지 않는다)
2. **(재)연결할 때마다 새 epoch 스냅샷**을 보낸다
3. 상담사 SDK 는 **새 epoch 스냅샷이 오면 복제본을 통째로 다시** 만든다
4. seq 공백·조각 유실·순서 꼬임 → 재동기화 요청 (19장)
5. 서버는 화면 내용을 저장하지 않는다 → **서버가 죽어도 잃을 화면 데이터가 없다** (상태는 고객 브라우저가 진실)

## 4. graceful shutdown (`application.yml`)
```yaml
server.shutdown: graceful
spring.lifecycle.timeout-per-shutdown-phase: 10s
```
배포 순서(롤링): 로드밸런서에서 빼기(헬스체크 실패 유도 또는 드레인) → SIGTERM → 연결이 1001 로 닫힘 → 클라이언트가 다른 서버로 → 새 버전 기동 → 다시 넣기.
한꺼번에 전부 재시작하면 모든 클라이언트가 동시에 재연결 → **jitter 가 서버를 살린다** (09장).

## 5. 캡스톤 — 전체를 설명해 보기

아래 질문에 **코드 위치까지** 짚으며 답할 수 있으면 이 튜토리얼을 끝낸 것이다. 말로 설명하거나 글로 써 보자 (Claude 에게 설명해 보고 피드백 받기도 좋다).

1. 고객이 "상담 시작"을 누른 순간부터 상담사 화면에 첫 화면이 뜨기까지, 오가는 HTTP 요청과 STOMP 프레임을 순서대로. (00-big-picture 의 시퀀스를 보지 않고)
2. 고객이 주민번호 칸에 타이핑할 때 원문이 **어디에도** 남지 않음을 보장하는 코드 경로 전부. (스냅샷·input·attr·ack)
3. 상담사가 "고급형" 플랜을 클릭했을 때, 고객 화면과 상담사 화면이 바뀌기까지. 동의가 없을 때는?
4. 300KB 스냅샷이 상담사에게 도착하기까지 거치는 크기 제한 층과 각 층의 값.
5. 한 고객이 보낸 프레임의 순서가 지켜지는 이유 — SDK 송신, Spring 수신·송신, 상담사 수신 각각.
6. 상담사의 토큰이 만료됐는데 화면만 보고 있었다면 무슨 일이 일어나나? 갱신을 했다면?
7. 서버 2대에서 강제 퇴장 API 가 A 로 들어왔는데 상담사는 B 에 있다. 어떻게 끊기나?
8. 서버 A 를 kill -9 했을 때 1분 동안 일어나는 일을 시간 순서로. (1절을 보지 않고)
9. 새 고객사가 "상담사는 평일 9~18시에만 원격 조작 가능" 규칙을 요구한다. 어디에 무엇을 추가하나? (05장 패턴)
10. 이 시스템에서 "아직 약한 곳" 세 가지와 개선 방향. (힌트: [ADVANCED_TOPICS](../../docs/ADVANCED_TOPICS.md))

# 14. 문자열 · UTF-8 · 바이트 · 바이너리, JSON · base64, 압축

## 이 장의 목표
- 문자열 길이와 **바이트 수**가 다른 이유(UTF-16 vs UTF-8)를 설명하고, 크기 한도를 바이트로 계산할 수 있다.
- JSON 이 텍스트라 생기는 제약과, 바이트를 텍스트에 싣는 **base64** 의 비용(+33%)을 안다.
- 압축이 잘 되는 데이터와 안 되는 데이터를 구분하고, 언제 압축할지 정할 수 있다.

## 프로젝트에서 이 장의 자리
스냅샷 JSON 은 수십~수백 KB 다. 서버 메시지 한도(18장)를 넘지 않으려면 **바이트로 재고, 압축하고, 그래도 크면 조각낸다.**
`web/sdk/src/bytes.ts`, `codec.ts` 가 이 장의 코드다.

---

## 1. 문자 · 문자열 · 바이트

- 컴퓨터는 **바이트**(0~255)만 안다. 글자를 바이트로 바꾸는 규칙 = **인코딩**.
- **UTF-8**: 웹의 표준. 영문 1바이트, 한글 3바이트, 이모지 4바이트.
- **JS 문자열**은 내부적으로 **UTF-16**: `.length` 는 UTF-16 단위 수. 이모지는 2칸(서로게이트 쌍).

| 문자열 | `.length` | UTF-8 바이트 |
|---|---|---|
| `abc` | 3 | 3 |
| `가나다` | 3 | **9** |
| `😀` | **2** | 4 |
| `상담 시작합니다 👋` | 11 | 27 |

→ "메시지 64KB 이하"를 `.length < 65536` 으로 검사하면 한글 페이지에서 **3배**를 넘긴다.
SDK 는 `utf8Bytes()`(TextEncoder)로 잰다. STOMP·HTTP 의 `content-length` 도 바이트다(08장 lab 출력에서 확인).

## 2. 텍스트 vs 바이너리

- WebSocket 프레임은 **text**(UTF-8 이어야 함)와 **binary** 두 종류가 있다.
- STOMP 는 텍스트 프로토콜이고 본문 끝을 `\0` 으로 표시한다 → 본문에 임의 바이트를 넣기 곤란하다.
- JSON 도 텍스트 → 압축된 바이트(gzip 결과)를 그대로 넣을 수 없다.

## 3. base64 — 바이트를 안전한 글자로

- 3바이트 → 4글자 (`A-Z a-z 0-9 + /`, 패딩 `=`). 어떤 텍스트 채널에도 실을 수 있다.
- 대가: **약 33% 커진다.**
- base64url: URL 에 안전하게 `+/` 대신 `-_`, 패딩 생략 → JWT 가 쓴다(11장).
- 함정: `btoa()` 는 "한 글자 = 한 바이트" 문자열만 받는다. 한글 문자열을 바로 넣으면 에러 → 먼저 UTF-8 바이트로 (`bytes.ts` 의 `toBase64`).

## 4. 압축

- **gzip(DEFLATE)**: 반복되는 패턴을 "앞의 그것"으로 바꿔 줄인다. 표준 API `CompressionStream('gzip')` 이 브라우저와 Node 양쪽에 있다.
- DOM 직렬화 JSON 은 `"tag":"li","attrs":{"class":` 같은 반복이 많아 **아주 잘 줄어든다**.

`npm run lab:14` 실측:
```
DOM 비슷한 JSON: 원본 59447B → gzip 3538B (6.0%) → base64 4720B
무작위 문자열:   거의 안 줄고, base64 로 오히려 커진다
```
| 언제 압축하나 | 언제 하지 않나 |
|---|---|
| 큰 텍스트(JSON, HTML, CSS) | 작은 메시지 (gzip 헤더 ~20B 가 더 크다) → SDK 는 **2KB 이상만** |
| 반복이 많은 데이터 | 이미 압축된 것(이미지·영상·zip) |
| 네트워크가 병목 | CPU 가 병목 (모바일 저사양에서 큰 압축은 화면을 버벅이게 할 수 있다) |

## 5. SDK 의 선택 (`codec.ts`)

```
프레임 JSON ─ 2KB 미만? ─예─▶ {k:'f', e:{...}}           (그대로)
     │ 아니오
     ▼
 gzip → base64 ─ 한도 이하? ─예─▶ {k:'z', d:'H4sI...'}   (압축)
     │ 아니오
     ▼
 base64 문자열을 조각 ─▶ {k:'c', id, i, n, d} × n       (18장)
```
- 압축·해제는 **비동기**다 → 순서 문제가 생긴다 (03장 "한 줄 세우기", 19장).
- 서버는 이 내용을 **풀어 보지 않고** 중계한다. 그래서 마스킹은 반드시 고객 브라우저에서 끝내야 한다 (22장).

## 자주 하는 실수
- `.length` 로 크기 한도 계산
- `btoa(한글)` → InvalidCharacterError
- `String.fromCharCode(...bigArray)` → 인자 개수 한도로 RangeError (그래서 `toBase64` 는 32KB 씩 자른다)
- 모든 메시지를 무조건 압축 → 작은 메시지가 커지고 CPU 낭비

## 확인 질문
1. 한글 20,000자로 된 JSON 은 64KB 한도 안에 들어가나?
2. gzip 결과를 base64 로 바꾸면 압축 효과가 사라지지 않나?
3. 이미지 data URL(이미 PNG)이 들어간 스냅샷을 또 gzip 하면?

<details><summary>답</summary>

1. 약 60,000바이트 + 구조 → 아슬아슬하거나 넘는다. 바이트로 재야 한다.
2. 33% 늘어나도 6% → 8% 수준이라 여전히 크게 이득이다 (DOM JSON 의 경우).
3. 그 부분은 거의 안 줄어든다. 큰 이미지는 URL 로만 보내는 게 낫다 (16장: canvas 는 20만 자 이하만 data URL).
</details>

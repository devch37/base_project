# 11. JWT — 구조 · 서명 · 만료 · 클레임, 서명 vs 암호화, Bearer vs 내부 API 키

## 이 장의 목표
- JWT 세 부분(헤더·페이로드·서명)을 손으로 만들고 읽을 수 있다.
- **서명은 암호화가 아니다**를 실제로 보여 줄 수 있다.
- 클레임 설계(무엇을 넣고 무엇을 빼나), 만료와 시계 오차를 다룰 수 있다.
- **Bearer 토큰(사용자용)** 과 **내부 API 발급 키(서버용)** 의 차이를 표로 설명할 수 있다.

## 프로젝트에서 이 장의 자리
고객사 서버가 `X-Api-Key` 로 우리 서버의 `/internal/tokens` 를 부르면 JWT 가 나온다.
브라우저는 그 JWT 를 STOMP CONNECT 의 `Authorization: Bearer` 에 넣는다 (12장).

## 1. 구조

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJjLTEwMCIsInJvbGUiOiJDVVNUT01FUiIsLi4ufQ . 3q2-7w...
└──── 헤더 ─────────┘   └──────────────── 페이로드(클레임) ─────────────────┘   └ 서명 ┘
   base64url(JSON)                    base64url(JSON)                      base64url(HMAC)
```
`JwtService.issue()` 가 만드는 페이로드:
```json
{
  "jti": "8b1c…",          // 토큰 고유 ID
  "iss": "chat-tutor",      // 발급자 — 검증 시 requireIssuer
  "sub": "c-100",           // 주체(누구) — userId
  "aud": ["chat-ws"],       // 대상 — "채팅 WebSocket 용". 다른 서비스 토큰 재사용 방지
  "iat": 1760000000,        // 발급 시각 (초)
  "exp": 1760000900,        // 만료 시각 (초) — 15분
  "tenant": "acme-bank",    // 우리가 정한 클레임들
  "role": "CUSTOMER",
  "rooms": ["r-1"]
}
```

## 2. 서명 vs 암호화

| | 서명 (JWS — 지금 쓰는 것) | 암호화 (JWE) |
|---|---|---|
| 누가 읽을 수 있나 | **누구나** (base64 디코드만 하면) | 키를 가진 쪽만 |
| 누가 고칠 수 있나 | 비밀키 가진 쪽만 (고치면 서명 불일치) | — |
| 보장하는 것 | **무결성·출처**: "우리가 만들었고 안 바뀌었다" | **기밀성** |

→ 페이로드에 **주민번호·전화번호·주소 같은 개인정보를 넣지 않는다.** (`npm run lab:11`, `JwtServiceTest.페이로드는_암호화가_아니라…`)

### HS256 vs RS256
- **HS256**(대칭): 같은 비밀키로 서명·검증. 발급자와 검증자가 같은 서버(우리처럼)면 충분.
- **RS256**(비대칭): 개인키로 서명, **공개키로 검증만**. 검증하는 서비스가 여럿인데 그들이 "발급 능력"까지 가지면 안 될 때. (공개키 배포: JWKS ⏭ 고급)

### ★ 검증할 때 반드시
1. **서명** — 그리고 `alg` 를 서버가 정한다. 토큰 헤더의 `"alg":"none"` 을 믿으면 서명 없는 위조 토큰이 통과한다 (jjwt 는 `verifyWith(key)` 로 거부).
2. **만료(exp)** — ★ 서버 간 **시계 오차** 허용(`clock-skew: 30s`). 발급 서버와 검증 서버 시계가 몇 초 달라도 갓 발급한 토큰이 거부되지 않게.
3. **발급자(iss)·대상(aud)**.
4. 필수 클레임 존재. 실패 이유는 로그에만 자세히, 클라이언트에는 뭉뚱그려 ("서명이 틀렸다"는 공격자에게 힌트).
5. 비밀키는 **최소 32바이트**. 짧으면 기동을 막는다(fail fast, `JwtService` 생성자).

## 3. 클레임 설계 — 무엇을 넣나

| 넣는다 | 넣지 않는다 |
|---|---|
| 잘 안 바뀌고 "검증 시점에 필요한" 것: userId, tenant, role, 고객의 방 | 자주 바뀌는 것: **상담사 배정**(이관·추가 배정이 수시로) → 서버에서 매번 조회 (`RoomRegistry`) |
| 짧은 만료 | 개인정보, 비밀번호, 내부 메모 |

상담사 배정을 토큰에 넣으면, 배정이 해제돼도 **옛 토큰으로 계속 들어올 수 있다.**

## 4. Bearer 토큰 vs 내부 API 발급 키

| | 내부 API 키 (`X-Api-Key`) | Bearer JWT |
|---|---|---|
| 누구의 신원? | **고객사 서버** | **최종 사용자** (고객·상담사) |
| 어디에 보관? | 고객사 서버의 환경 변수·비밀 저장소 | 사용자 브라우저 **메모리** |
| 수명 | 길다 (수개월, 교체 주기 운영) | 짧다 (분 단위) |
| 할 수 있는 일 | 방 생성, **아무 사용자의 토큰 발급**, 강제 퇴장 | 정해진 방에서 채팅·화면 공유 |
| 유출되면 | 그 고객사 **모든 사용자 사칭 가능** — 치명적 | 그 사용자·그 방·만료까지 |
| 검증 | 상수 시간 비교 (`MessageDigest.isEqual`, 타이밍 공격 방지) | 서명·만료·클레임 |

"Bearer" = **가진 사람(bearer)을 그 사용자로 믿는다.** 탈취되면 그대로 사칭된다 → HTTPS 필수, 짧은 만료.

**API 키는 절대 브라우저에 두지 않는다.** 그래서 `web/tenant-backend` 라는 중간 서버가 있다.
브라우저 → 고객사 서버(로그인 세션 확인) → 우리 서버(API 키). 실습 서버는 로그인 확인을 생략했다는 점만 다르다.

## 자주 하는 실수
- 페이로드에 개인정보 → 로그·프록시·브라우저 어디서든 읽힌다.
- `exp` 없는 토큰 → 영원히 유효.
- 토큰의 `alg` 를 그대로 믿기.
- API 키를 프론트 환경 변수(`VITE_*`)에 넣기.
- 비밀키를 yml 에 하드코딩하고 커밋 (`application.yml` 은 `${CHAT_JWT_SECRET:dev-only…}` — 운영에서는 반드시 환경 변수로).

# 08. 예외 처리와 로깅

## 예외 처리 철학

NestJS에서 에러는 **던지면 됩니다.** 프레임워크가 잡아서 HTTP 응답으로 바꿔줍니다.
`try/catch` 로 감싸서 `res.status(400).json(...)` 를 직접 하는 건 안티패턴입니다.

```ts
// ✅ 이렇게
if (!user) throw new NotFoundException('사용자를 찾을 수 없습니다.');

// ❌ 이렇게 하지 마세요
if (!user) return res.status(404).json({ error: '...' });
```

---

## 내장 HTTP 예외

`@nestjs/common` 이 상태코드별 예외 클래스를 제공합니다:

| 예외 | 코드 | 언제 |
|------|------|------|
| `BadRequestException` | 400 | 잘못된 입력 (검증은 ValidationPipe가 자동) |
| `UnauthorizedException` | 401 | 인증 안 됨 / 토큰 무효 |
| `ForbiddenException` | 403 | 인증됐지만 권한 없음 |
| `NotFoundException` | 404 | 리소스 없음 |
| `ConflictException` | 409 | 중복 (이메일 등) |
| `UnprocessableEntityException` | 422 | 형식은 맞지만 의미상 처리 불가 |
| `RequestTimeoutException` | 408 | 타임아웃 |
| `InternalServerErrorException` | 500 | 서버 오류 |

이 프로젝트에서 실제로 던지는 곳:
- `users.service.ts`: `ConflictException` (이메일 중복), `NotFoundException`
- `posts.service.ts`: `NotFoundException`, `ForbiddenException` (소유권)
- `auth.service.ts`: `UnauthorizedException` (로그인 실패)

    super({
      message: '잔액이 부족합니다.',
      code: 'INSUFFICIENT_BALANCE',
      current,
      required,
    });
  }
}

## 전역 예외 필터

`src/common/filters/all-exceptions.filter.ts` — `@Catch()` (인자 없음 = 모든 예외):

```ts
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const { status, error, message } = this.normalize(exception);

    // 5xx는 스택까지, 4xx는 한 줄만 로깅 (로그 노이즈 관리)
    if (status >= 500) {
      this.logger.error(`${req.method} ${req.url} → ${status}`, exception.stack);
    } else {
      this.logger.warn(`${req.method} ${req.url} → ${status} ${message}`);
    }

    response.status(status).json({
      success: false, statusCode: status, error, message,
      timestamp: new Date().toISOString(), path: request.url,
    });
  }
}
```

`normalize()` 가 세 가지를 구분:
1. `HttpException` → status/message 그대로
2. `QueryFailedError` (TypeORM, 예: UNIQUE 위반) → 409 로 매핑 + **드라이버 메시지는 숨김**
3. 알 수 없는 에러 → 500 + **"서버 내부 오류" 만 노출** (스택/쿼리는 로그에만)

> 프로덕션에서 내부 에러 메시지를 클라이언트에 노출하면 정보 유출입니다.
> "로그엔 전부, 응답엔 최소한" 이 원칙.

## 응답 형태 일관성

성공: `TransformInterceptor` 가 `{ success: true, data, meta?, timestamp, path }`
실패: `AllExceptionsFilter` 가 `{ success: false, statusCode, error, message, timestamp, path }`

프론트엔드는 `res.success` 하나만 보면 분기할 수 있습니다.

## 로깅

### 기본 Logger

```ts
import { Logger } from '@nestjs/common';

@Injectable()
export class PostsService {
  private readonly logger = new Logger(PostsService.name);  // 컨텍스트 이름

  create() {
    this.logger.log('게시글 생성됨');
    this.logger.warn('제목이 비어 있음');
    this.logger.error('저장 실패', stack);
    this.logger.debug('디버그 정보');   // 개발에서만
    this.logger.verbose('상세');
  }
}
```

`LoggingInterceptor` 가 모든 요청을 `[HTTP] GET /api/posts 200 +23ms` 형태로 남깁니다.

### 로그 레벨 제어 (main.ts)

```ts
const app = await NestFactory.create(AppModule, {
  logger: isProd
    ? ['error', 'warn', 'log']       // 운영: debug/verbose 끔
    : ['error', 'warn', 'log', 'debug', 'verbose'],
});
```

### 실무: 구조화된 JSON 로깅

기본 Logger는 사람이 읽는 텍스트입니다. 운영에서는 로그 수집기(ELK, Datadog, CloudWatch)가
파싱하기 좋은 **JSON 로그**를 씁니다. `nestjs-pino` 로 교체하는 게 표준:

```ts
// 개념 (별도 패키지 필요 — 이 프로젝트엔 미포함)
import { LoggerModule } from 'nestjs-pino';

@Module({
  imports: [LoggerModule.forRoot({
    pinoHttp: {
      level: process.env.LOG_LEVEL ?? 'info',
      redact: ['req.headers.authorization'],   // 민감 정보 마스킹
      // 요청마다 reqId 자동 부여 → 로그 추적 가능
    },
  })],
})
```

핵심 개념:
- **상관관계 ID (correlation/request ID)**: 한 요청의 모든 로그를 묶는 ID.
  마이크로서비스 간에도 전파하면 분산 추적이 됩니다.
- **민감 정보 마스킹**: 비밀번호, 토큰, 주민번호는 로그에 절대 남기지 않기.
- **로그 레벨 규율**: `error`(즉시 알림), `warn`(주시), `info`(주요 이벤트), `debug`(개발용).

## 관찰 가능성 (Observability) 3요소

| | 무엇 | 도구 예 |
|--|------|---------|
| **로그** | 개별 사건 기록 | pino, ELK, Loki |
| **메트릭** | 수치 집계 (요청 수, p99 지연, 에러율) | Prometheus + Grafana, `@willsoto/nestjs-prometheus` |
| **트레이스** | 요청이 서비스들을 지나는 경로 | OpenTelemetry, Jaeger |

`/api/health`, `/api/health/ready` (`health.controller.ts`) 는 이 중 가장 기본인
"살아있음/준비됨" 신호입니다.

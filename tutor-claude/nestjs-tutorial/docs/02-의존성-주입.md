# 02. 의존성 주입 (Dependency Injection, DI)

## 문제: `new` 를 직접 쓰면 생기는 일

```ts
class PostsService {
  private repo = new PostRepository(new Database(config.dbUrl)); // ❌
}
```

- `PostsService` 를 테스트하려면 진짜 DB가 필요함
- `Database` 구현을 바꾸면 `PostsService` 도 고쳐야 함
- 같은 `Database` 인스턴스를 여러 서비스가 공유하기 어려움

## 해결: "필요한 걸 말하면, 프레임워크가 만들어서 넣어준다"

```ts
@Injectable()
export class PostsService {
  constructor(
    @InjectRepository(Post) private readonly postsRepo: Repository<Post>,
  ) {}
  //  ↑ "나는 Repository<Post> 가 필요하다" 라고 생성자에 선언만 함
}
```

NestJS의 **IoC 컨테이너**가 앱 시작 시:
1. 모든 `@Injectable()` / 컨트롤러의 생성자 파라미터 타입을 읽고
2. 의존성 그래프를 계산해서
3. 올바른 순서로 인스턴스를 만들어 주입합니다.

이게 가능한 이유: `tsconfig.json` 의 `emitDecoratorMetadata: true` 가
**생성자 파라미터의 타입 정보를 런타임까지 남겨주기** 때문입니다.
(그래서 `reflect-metadata` 를 `main.ts` 최상단에서 import 하는 것)

## 프로바이더 등록 방식 4가지

`app.module.ts` 와 `common/mailer/mailer.module.ts` 에서 실제 예시를 볼 수 있습니다.

### 1. `useClass` — 클래스를 그대로 (가장 흔함)

```ts
providers: [PostsService]
// = providers: [{ provide: PostsService, useClass: PostsService }]
```

`app.module.ts` 의 전역 가드 등록도 이 방식:
```ts
{ provide: APP_GUARD, useClass: JwtAuthGuard }
```

### 2. `useValue` — 이미 만들어진 값/객체

```ts
{ provide: MAILER_OPTIONS, useValue: { from: 'no-reply@x.com' } }
```
테스트에서 mock을 넣을 때도 이걸 씁니다:
```ts
{ provide: HashingService, useValue: { hash: jest.fn(), compare: jest.fn() } }
```

### 3. `useFactory` — 다른 프로바이더에 의존해서 동적으로 생성

```ts
CacheModule.registerAsync({
  inject: [ConfigService],                          // 팩토리에 주입할 것
  useFactory: (cfg: ConfigService) => ({ ttl: cfg.get('cache.ttl') }),
})
```
`mailer.module.ts` 의 `forRootAsync` 도 이 패턴입니다.

### 4. `useExisting` — 기존 프로바이더에 별칭 붙이기

```ts
{ provide: 'LOGGER', useExisting: MyLoggerService }
```

## 주입 토큰 (Injection Token)

"무엇을 주입할지" 식별하는 키입니다.

- **클래스 자체**가 토큰: `constructor(private svc: PostsService)` → `PostsService`
- **문자열/심볼** 토큰: 인터페이스는 런타임에 사라지므로, 인터페이스를 주입하려면
  문자열 토큰이 필요합니다.

```ts
// mailer.types.ts
export const MAILER_OPTIONS = 'MAILER_OPTIONS';

// mailer.service.ts
constructor(@Inject(MAILER_OPTIONS) private readonly options: MailerOptions) {}
```

- **`ConfigType` + `KEY`** (설정 네임스페이스, 09장):
```ts
constructor(
  @Inject(jwtConfig.KEY) private readonly cfg: ConfigType<typeof jwtConfig>,
) {}
```

## 스코프 (Scope)

| 스코프 | 인스턴스 개수 | 언제 |
|--------|--------------|------|
| `DEFAULT` (싱글턴) | 앱 전체에 1개 | 99% 이 경우. 상태 없는 서비스 |
| `REQUEST` | 요청마다 새로 | 요청별 컨텍스트(현재 사용자, 트레이스 ID)를 프로바이더가 직접 들고 있어야 할 때 |
| `TRANSIENT` | 주입될 때마다 새로 | 드묾 |

```ts
@Injectable({ scope: Scope.REQUEST })
```

⚠️ `REQUEST` 스코프는 **전염됩니다.** 이걸 주입받는 모든 프로바이더도 요청 스코프가 되어
성능에 영향을 줍니다. 되도록 `@CurrentUser()` 처럼 파라미터로 넘기는 방식을 쓰세요.

## 순환 의존성 (Circular Dependency)

`A` 가 `B` 를, `B` 가 `A` 를 주입받으면 컨테이너가 순서를 못 정합니다.

```ts
// 해결책 1 (임시방편): forwardRef
constructor(@Inject(forwardRef(() => BService)) private b: BService) {}

// 해결책 2 (근본): 공통 로직을 제3의 모듈로 빼서 순환을 끊기 ← 권장
```

이 프로젝트는 `CommentsModule → PostsModule` 단방향이라 순환이 없습니다.
설계 시 "의존성 방향을 한쪽으로" 유지하세요.

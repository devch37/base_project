# 01. 핵심 빌딩블록 — 모듈 · 컨트롤러 · 프로바이더

NestJS 앱은 세 가지 조각의 반복입니다. 이 셋만 이해하면 절반은 끝난 겁니다.

```
Module      = 관련된 것들을 묶는 상자 (기능 단위)
Controller  = HTTP 요청을 받는 곳 (경로 → 메서드 매핑)
Provider    = 실제 일을 하는 것 (주로 Service, 그 외 Repository/Factory 등)
```

요청 흐름: **HTTP 요청 → Controller → Service(Provider) → DB/외부 → 응답**

---

## 1) 컨트롤러 (Controller)

`src/modules/posts/posts.controller.ts` 를 열어 보세요.

```ts
@Controller('posts')          // 이 컨트롤러의 모든 경로 앞에 /posts
export class PostsController {
  constructor(private readonly postsService: PostsService) {}  // ← 주입(02장)

  @Get()                       // GET /posts
  findAll(@Query() query: QueryPostsDto) {
    return this.postsService.findAll(query);
  }

  @Get(':id')                  // GET /posts/:id
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.postsService.findOne(id, true);
  }

  @Post()                      // POST /posts
  create(@Body() dto: CreatePostDto, @CurrentUser('id') userId: number) {
    return this.postsService.create(dto, userId);
  }
}
```

### 자주 쓰는 데코레이터

| 데코레이터 | 용도 |
|-----------|------|
| `@Get() @Post() @Patch() @Put() @Delete()` | HTTP 메서드 + 경로 |
| `@Param('id')` | URL 경로 변수 (`/posts/:id`) |
| `@Query()` | 쿼리스트링 (`?page=2`) |
| `@Body()` | 요청 본문(JSON) |
| `@Headers()` `@Req()` `@Res()` | 헤더 / 원본 요청·응답 객체 |
| `@HttpCode(204)` | 응답 상태코드 지정 |
| `@CurrentUser()` | (우리가 만든) 인증된 사용자 — 07장 |

### 컨트롤러가 하지 말아야 할 것

컨트롤러는 **"HTTP를 도메인 호출로 번역"만** 합니다.
비즈니스 규칙(중복 검사, 권한 판단, 계산)은 전부 Service로 내려보내세요.
컨트롤러가 두꺼워지면 테스트가 어려워지고 재사용이 안 됩니다.

## 2) 프로바이더 / 서비스 (Provider / Service)

`src/modules/posts/posts.service.ts`:

```ts
@Injectable()                  // "이 클래스는 DI 컨테이너가 관리한다"
export class PostsService {
  constructor(
    @InjectRepository(Post) private readonly postsRepo: Repository<Post>,
    @Inject(CACHE_MANAGER) private readonly cache: Cache,
  ) {}

  async create(dto: CreatePostDto, authorId: number): Promise<Post> {
    // ... 실제 로직
  }
}
```

- `@Injectable()` 이 붙은 클래스는 다른 곳에 **주입**될 수 있고, 다른 것을 **주입받을** 수 있습니다.
- Service는 상태를 갖지 않는(stateless) **싱글턴**입니다. 기본적으로 앱 전체에 인스턴스 1개.

## 3) 모듈 (Module)

`src/modules/posts/posts.module.ts`:

```ts
@Module({
  imports: [TypeOrmModule.forFeature([Post, Tag])],  // 이 모듈이 쓸 다른 모듈
  controllers: [PostsController],                     // 이 모듈의 컨트롤러
  providers: [PostsService],                          // 이 모듈의 프로바이더
  exports: [PostsService],                            // 다른 모듈에 공개할 것
})
export class PostsModule {}
```

### `@Module` 4대 속성

| 속성 | 의미 | 비유 |
|------|------|------|
| `imports` | 다른 모듈을 가져옴 (그 모듈이 `exports` 한 것을 쓸 수 있게 됨) | "다른 팀에서 API 받아오기" |
| `controllers` | 이 모듈에 속한 컨트롤러 | "우리 팀 접수창구" |
| `providers` | 이 모듈 안에서 주입 가능한 프로바이더 | "우리 팀 직원" |
| `exports` | 우리 프로바이더 중 외부에 빌려줄 것 | "다른 팀에 파견 가능한 직원" |

### 중요: 모듈 경계 = 캡슐화 경계

`PostsModule` 이 `PostsService` 를 `exports` 하지 않으면, `CommentsModule` 에서
`PostsService` 를 주입받을 수 없습니다. → `comments.module.ts` 가
`imports: [PostsModule]` 하고, `posts.module.ts` 가 `exports: [PostsService]` 해야
연결됩니다. (실제 코드 확인해 보세요)

이 강제된 경계 덕분에 "누가 누구에게 의존하는지"가 코드에 명시적으로 드러납니다.

## 4) 루트 모듈

`src/app.module.ts` 가 최상위입니다. 모든 도메인 모듈 + 인프라 모듈을 여기서 `imports`.

```ts
@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true, ... }),   // 설정
    TypeOrmModule.forRootAsync({ ... }),              // DB
    UsersModule, AuthModule, PostsModule, CommentsModule, // 도메인
    // ...
  ],
})
export class AppModule {}
```

앱은 이 루트에서 시작해 **모듈의 트리**로 펼쳐집니다.

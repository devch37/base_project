# 01. C의 철학과 메모리 모델

> 목표: **"왜 C는 이렇게 위험하게 설계됐는가"** 를 이해하고, 실행 중인 프로그램의 메모리 지도를 그린다.

---

## 0. 초등학생 버전 비유

C는 **레고 블록**이 아니라 **찰흙과 조각칼**입니다.

- 레고(파이썬/자바): 정해진 모양의 블록만 끼울 수 있어요. 손을 다칠 일이 없죠. 대신 느리고, 블록 사이 빈틈이 생겨요.
- 찰흙+조각칼(C): 원하는 어떤 모양이든 만들 수 있고, 아주 정밀합니다. 대신 **조각칼에 손을 벨 수 있어요.**

C를 만든 사람들은 "프로그래머는 자기가 뭘 하는지 안다"고 **믿기로** 했습니다.
그래서 "이거 위험한데요?"라고 막지 않습니다. 이 믿음이 C를 빠르게 만들었고, 동시에 위험하게 만들었습니다.

---

## 1. C는 왜 만들어졌나 (1972, 벨 연구소)

- **목적**: 운영체제(UNIX)를 어셈블리 대신 이식 가능한 언어로 짜기 위해.
- 그래서 C의 모든 설계 결정은 이 문장으로 요약됩니다:
  > **"어셈블리만큼 하드웨어에 가깝되, 기계마다 다시 짜지 않아도 되게."**
- 결과적으로 C에는 이런 것들이 **없습니다**:
  - 가비지 컬렉터 (메모리는 네가 관리해라)
  - 배열 범위 검사 (검사 비용을 강제하지 않는다)
  - 예외 (에러는 반환값으로 알려라)
  - 문자열 타입 (문자열은 그냥 `char` 배열이다)
  - 객체/클래스 (구조체 + 함수면 충분하다)
- 대신 이런 게 있습니다: **포인터** — 메모리 주소를 값처럼 다루는 능력. C의 힘과 위험의 원천.

### "Trust the programmer" 의 대가: Undefined Behavior(UB)

C 표준은 "이런 짓을 하면 무슨 일이 일어날지 **우리는 정의하지 않는다**"는 목록을 둡니다.
범위를 넘은 배열 접근, `NULL` 역참조, 부호 있는 오버플로우, 초기화 안 한 값 읽기 등.

UB가 발생하면 컴파일러는 **"그런 일은 절대 안 일어난다"고 가정하고 최적화**합니다.
그래서 UB는 단순 크래시가 아니라, **엉뚱한 곳에서 조용히 이상하게 동작**할 수 있습니다.
16장 전체가 이 주제입니다. 지금은 "UB = 밟으면 안 되는 지뢰"로만 기억하세요.

## 2. 실행 중인 프로그램의 메모리 지도

`./bin/01_memory_map` 을 실행하면 아래 각 구역의 실제 주소가 출력됩니다.
프로그램이 실행되면 OS가 이런 가상 주소 공간을 만들어 줍니다 (숫자는 개념적):

```
높은 주소
┌─────────────────────────────┐
│           스택 (stack)       │  지역 변수, 함수 호출 정보. 함수 진입 시 자라고 복귀 시 사라짐.
│              ↓ 아래로 자람    │  자동 관리. 빠름. 크기 제한(보통 8MB). 넘치면 stack overflow.
│                             │
│         (빈 공간)            │
│                             │
│              ↑ 위로 자람      │  malloc/free 로 직접 관리. 크고 유연. 느림.
│           힙 (heap)          │  관리 실수 = 누수 / dangling / double free (8장)
├─────────────────────────────┤
│   BSS  (초기화 안 된 전역)     │  0으로 채워짐. 파일 크기엔 안 들어감.
├─────────────────────────────┤
│   Data (초기화된 전역/static) │  프로그램 시작 시 초기값으로 채워짐.
├─────────────────────────────┤
│   Text / Code (읽기 전용)     │  기계어 명령. 문자열 리터럴("hello")도 보통 여기(읽기전용).
└─────────────────────────────┘
낮은 주소
```

### 이 지도가 설명해 주는 것들

- **왜 지역 변수 주소를 반환하면 안 되나** (5장) — 함수가 끝나면 그 스택 구역은 다음 함수가 덮어씀.
- **왜 `char *s = "hi"; s[0] = 'H';` 가 크래시하나** (7장) — `"hi"` 는 Text 근처 읽기 전용 구역.
- **왜 `malloc` 은 느리고 스택 변수는 빠른가** — 스택은 포인터 하나 움직이면 끝. 힙은 빈 공간을 찾아야 함.
- **왜 재귀가 너무 깊으면 죽나** — 스택 구역이 힙 쪽으로 계속 자라다 한계를 넘음.

## 3. "모든 것은 비트다" — 타입은 해석 규칙일 뿐

메모리에는 그냥 0과 1이 있습니다. **타입은 "이 바이트들을 어떻게 읽을지"에 대한 약속**입니다.

`./bin/01_reinterpret` 예제는 똑같은 4바이트를
`int` 로도, `float` 로도, `unsigned char` 4개로도 읽습니다. 값이 완전히 다르게 나옵니다.

```c
float f = 1.0f;
unsigned int bits;
memcpy(&bits, &f, sizeof bits);   /* 같은 비트를 정수로 재해석 */
printf("1.0f 의 비트 패턴: 0x%08X\n", bits);   /* 0x3F800000 (IEEE 754) */
```

이게 C의 정신입니다: **메모리는 날것이고, 타입은 렌즈다.**

## 4. C 표준의 존재 — "어느 C를 쓰는가"

C에는 버전이 있습니다. 오픈소스 기여 시 중요합니다(21장).

| 표준 | 연도 | 실무에서 의미 |
|------|------|--------------|
| C89 / C90 (ANSI C) | 1989 | 아주 오래된/이식성 극한 프로젝트(예: 일부 임베디드). 변수를 블록 맨 앞에 선언해야 함. |
| **C99** | 1999 | `//` 주석, `for(int i...)`, `<stdint.h>`, 가변 길이 배열(VLA), `bool`. 사실상 최소 기준선. |
| **C11** | 2011 | `<threads.h>`, `<stdatomic.h>`, `_Static_assert`, 익명 구조체. **이 코스의 기본.** |
| C17 | 2018 | C11의 버그 픽스판. 새 기능 없음. GCC/Clang 기본값. |
| C23 | 2024 | `true`/`false`/`nullptr` 키워드화, `#embed`, `[[attributes]]`. 아직 도입 중. |

컴파일은 `-std=c11` 처럼 지정합니다. 지정 안 하면 컴파일러 기본값(요즘은 gnu17)이 쓰입니다.

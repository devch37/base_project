# 09. 구조체·공용체·열거형·메모리 정렬

> 목표: 구조체의 메모리 레이아웃(패딩/정렬), 공용체와 태그 유니온, 열거형의 함정,
> 불투명 포인터로 캡슐화하기.

---

## 0. 초등학생 버전 비유

구조체는 **필통**입니다. 연필, 지우개, 자를 한 칸씩 넣어 하나로 들고 다닙니다.

그런데 필통에는 칸막이 규칙이 있어요: 큰 물건은 "정해진 위치"에서 시작해야 합니다.
그래서 작은 물건 뒤에 **빈 칸(패딩)** 이 생깁니다. 물건 순서를 잘 배치하면 필통이 작아집니다.

공용체는 **하나의 칸을 여러 용도로 번갈아 쓰는 것** — 연필도 되고 지우개도 되는데,
동시에 둘 다는 안 되는 마법 칸입니다.

---

## 1. 구조체 기본

```c
struct Point { int x; int y; };          // 정의
struct Point p = { .x = 3, .y = 4 };     // 지정 초기화 (C99). 나머지는 0
struct Point q = { 3, 4 };               // 순서대로
p.x = 10;                                // 멤버 접근
struct Point *pp = &p;
pp->y = 20;                              // (*pp).y 의 문법 설탕

typedef struct { int x, y; } Point;       // typedef 로 이름 짧게 (실무 흔함)
```

- 구조체는 **값 타입**입니다. 대입(`q = p`)은 **멤버별 복사**. 함수 인자도 복사(큰 건 `const T *`).
- 배열 멤버는 복사됨. **포인터 멤버는 주소만 복사**(얕은 복사) → 깊은 복사는 직접 (15장).
- 유연 배열 멤버(flexible array member): `struct S { size_t n; int items[]; };` +
  `malloc(sizeof(struct S) + n * sizeof(int))` — 헤더+데이터를 한 번에 할당 (실무 관용구).

## 2. 메모리 정렬과 패딩

CPU는 "N바이트 값은 N의 배수 주소에서" 읽는 걸 좋아합니다(또는 강제합니다).
컴파일러는 각 멤버가 정렬되도록 **패딩 바이트**를 끼워 넣습니다.

```c
struct Bad {          //  오프셋
    char  a;          //  0        (1바이트)
    // 3바이트 패딩             1..3
    int   b;          //  4        (int 는 4의 배수 주소)
    char  c;          //  8
    // 3바이트 패딩             9..11 (구조체 크기를 4의 배수로: 배열 정렬 위해)
};                    //  sizeof = 12

struct Good {
    int   b;          //  0
    char  a;          //  4
    char  c;          //  5
    // 2바이트 패딩             6..7
};                    //  sizeof = 8   ← 멤버를 큰 것부터 배치하면 33% 절약
```

`./bin/09_layout` 가 `offsetof` 로 각 멤버 위치와 패딩을 출력합니다.

### 실무 포인트

- **큰 멤버(8) → 작은 멤버(1) 순서**로 선언하면 패딩이 줄어듭니다. 캐시에도 유리.
- `_Alignof(T)` (C11): 타입의 정렬 요구. `_Alignas(N)`: 정렬 강제.
- `#pragma pack(1)` / `__attribute__((packed))`: 패딩 제거. **위험** — 정렬 안 된 접근이
  일부 아키텍처에서 크래시하거나 느려짐. 파일/네트워크 포맷엔 packed 대신 **바이트 단위
  직렬화 함수**를 쓰세요 (16장).
- 구조체를 `memcmp` 로 비교하지 마세요 — 패딩 바이트는 쓰레기라 같은 값도 다르게 나옵니다.

## 3. 공용체와 태그 유니온

```c
union Value {          // 모든 멤버가 같은 메모리를 공유. sizeof = 가장 큰 멤버
    int    i;
    double d;
    char   bytes[8];
};
union Value v;
v.d = 3.14;
v.i;                   // UB에 가까움: 마지막에 쓴 멤버(d)가 아닌 걸 읽음
                       // (예외: memcpy 없이 재해석하는 "type punning"은 C에선 관용적으로 허용,
                       //  단 서로 호환되는 초기 멤버가 아니면 조심)
```

**태그 유니온(discriminated union)** — C에서 "여러 타입 중 하나"를 표현하는 정석:

```c
typedef struct {
    enum { V_INT, V_STR, V_NULL } tag;   // 지금 무엇인지 기록
    union {
        long        as_int;
        char       *as_str;
    };                                    // C11 익명 union
} Json;

// 사용: 반드시 tag 를 먼저 확인
switch (j.tag) {
case V_INT: printf("%ld", j.as_int); break;
case V_STR: printf("%s",  j.as_str); break;
case V_NULL: printf("null"); break;
}
```

`./bin/09_tagged_union` 가 미니 JSON 값 타입으로 이 패턴을 구현합니다. (22장 캡스톤에서 재사용)

## 4. 열거형 (enum)

```c
enum Color { RED, GREEN, BLUE };          // RED=0, GREEN=1, BLUE=2
enum Status { OK = 200, NOT_FOUND = 404 };// 명시적 값
enum { MAX_LINE = 4096 };                 // 이름 없는 enum = "타입 있는 #define" (배열 크기 등에 유용)
```

함정:
- `enum` 의 실제 타입은 **구현이 정하는 정수 타입**(보통 `int`). 크기가 보장 안 됨.
- 범위 밖 값을 담을 수 있음: `enum Color c = 99;` 는 합법. `switch` 에서 `default` 를 두세요.
- C의 enum은 이름 충돌에 약함(같은 스코프). 접두사를 붙이세요: `COLOR_RED`.
- C23은 `enum Color : uint8_t { ... }` 로 기반 타입 지정 가능.

## 5. 불투명 포인터(opaque pointer) — C의 캡슐화

헤더에는 **구조체 이름만**, 정의는 `.c` 에 숨깁니다. 사용자는 내부를 못 봅니다.

```c
// counter.h  (공개)
typedef struct Counter Counter;          // "불완전 타입". 크기 모름 → 포인터로만 사용 가능
Counter *counter_new(void);
void     counter_inc(Counter *c);
long     counter_get(const Counter *c);
void     counter_free(Counter *c);

// counter.c  (비공개)
struct Counter { long value; pthread_mutex_t lock; /* 내부 마음대로 */ };
```

장점: 내부 구조를 바꿔도 사용자 코드 재컴파일 불필요(ABI 안정), 캡슐화, 의존성 격리.
`FILE *`, `sqlite3 *`, `pthread_*` 전부 이 패턴입니다. 11장에서 직접 빌드합니다.

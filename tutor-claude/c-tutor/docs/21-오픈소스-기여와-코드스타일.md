# 21. 오픈소스 기여와 코드 스타일

> 목표: 낯선 C 프로젝트에 처음 패치를 낼 때 알아야 할 것들 —
> 표준 버전 파악, 스타일 맞추기, 빌드/테스트, 커밋·PR 예절, 리뷰 대응.

## 0. 초등학생 버전 비유

남의 집에 놀러 가면 **그 집 규칙**을 따릅니다. 신발을 벗는 집인지, 소파에 앉아도 되는지.
오픈소스도 똑같아요. 내 스타일을 고집하지 말고, **그 프로젝트가 이미 하는 방식**을 그대로 따라 합니다.
그게 좋은 손님(=기여자)입니다.

## 1. 프로젝트 파악: 처음 30분

새 C 저장소를 받으면 이 순서로 봅니다.

```bash
ls                          # README, LICENSE, CONTRIBUTING.md, CHANGELOG
cat CONTRIBUTING.md          # 있으면 이게 정답지. 스타일/테스트/PR 규칙
cat README* | head -60       # 빌드 방법, 의존성
ls .github/workflows/ .gitlab-ci.yml   # CI 가 뭘 검사하는지 = 통과해야 할 기준

# 빌드 시스템?
ls Makefile CMakeLists.txt configure meson.build Makefile.am

# C 표준 버전?
grep -rE 'std=c[0-9]+|C_STANDARD|-ansi' Makefile* CMakeLists.txt configure.ac 2>/dev/null

# 스타일 설정?
ls .clang-format .editorconfig .clang-tidy
cat .clang-format 2>/dev/null

# 경고 수준?
grep -rE '\-W(all|extra|error)' Makefile* CMakeLists.txt

# 테스트는 어떻게 도나?
grep -iE 'test|check' Makefile CMakeLists.txt; ls tests/ test/ t/
```

빌드 → 테스트 통과를 **먼저** 확인하세요. 내 변경 전 상태가 green이어야 비교가 됩니다.

## 2. C 표준 버전이 중요한 이유

프로젝트마다 "쓸 수 있는 문법"이 다릅니다.

| 프로젝트가 C89면 | 안 됨 |
|---|---|
| `// 주석` | `/* */` 만 |
| `for (int i = 0; ...)` | 변수를 블록 맨 앞에 선언 |
| `//` , 가변 길이 배열, `<stdint.h>`, `bool` | 전부 못 씀 |
| 지정 초기화 `{ .x = 1 }` | 순서대로만 |

- **리눅스 커널**: GNU C (C89 + GNU 확장 다수). 최근 C11 일부 허용.
- **SQLite**: 극한의 이식성. C89 호환. 컴파일러 10종 이상에서 테스트.
- **libcurl**: C89 기반, 최근 C99 일부.
- **대부분의 신규 프로젝트**: C11 또는 C17.
- **git**: C99 (일부 C89 잔재).

기여 전에 **그 프로젝트의 표준으로 컴파일**해 보세요: `cc -std=c89 -pedantic-errors ...`.

## 3. 스타일 맞추기

CONTRIBUTING이나 `.clang-format` 이 있으면 그대로. 없으면 **주변 코드를 흉내** 냅니다.

관찰 포인트:
- 들여쓰기: 탭 vs 스페이스, 폭 (커널=탭8, 다수=스페이스4)
- 중괄호: 함수는 다음 줄(Allman) vs 같은 줄(K&R). 제어문은?
- 포인터: `int *p` vs `int* p` vs `int*p`
- 이름: `snake_case`(대부분) vs `camelCase`, 상수 `UPPER`, 타입 접미사 `_t`
- 한 줄 길이: 80 (커널/전통) vs 100 vs 120
- 함수 사이 빈 줄, 파일 헤더 주석, 저작권 표기

```bash
# clang-format 이 있으면 내 변경분만 포맷
git clang-format HEAD~1          # 마지막 커밋에서 바뀐 줄만 포맷
# 또는 특정 파일
clang-format -i src/foo.c && git diff   # 의도치 않은 대량 변경이 없는지 확인
```

> **금지**: "이왕 건드리는 김에" 파일 전체를 재포맷하지 마세요. 리뷰어가 진짜 변경을
> 못 찾습니다. 포맷 변경과 로직 변경은 **별도 커밋/PR**로.

## 4. 이 코스의 `.clang-format` 과 스타일 예시

`c-tutor/.clang-format` 은 오픈소스에서 흔한 중도 스타일입니다:
4칸 스페이스, 100자, 포인터 오른쪽 정렬, K&R 중괄호. 적용:

```bash
cd c-tutor
clang-format -i examples/**/*.c docs/../examples/*/*.c
```

일반적으로 합의된 좋은 습관 (프로젝트가 다르게 하지 않는 한):
- 함수는 한 가지 일만, 화면 한 페이지 이내
- 헬퍼·파일 전역에 `static`
- `const` 를 적극적으로
- 이른 반환(early return)으로 중첩 줄이기, 정리는 `goto cleanup`
- 매직 넘버 대신 `enum`/명명 상수
- 모든 `malloc` 에 짝이 되는 `free`, 소유권 주석
- 경고 0 (`-Wall -Wextra`), 가능하면 `-Werror`

## 5. 커밋과 PR

### 커밋 메시지 (git 관례)
```
component: 한 줄 요약 (50자 내외, 명령형, 마침표 없음)

왜 이 변경이 필요한지, 무엇을 바꿨는지 본문에 설명 (72자로 줄바꿈).
어떻게 테스트했는지도.

Fixes: #1234
Signed-off-by: Your Name <you@example.com>   (프로젝트가 DCO 요구 시)
```

- 커밋 하나 = 논리적 변경 하나. "WIP", "fix typo" 커밋은 rebase로 정리(`git rebase -i`).
- 리팩터링과 기능 추가를 한 커밋에 섞지 마세요.

### PR 전 체크리스트
- [ ] 브랜치를 최신 `main`/`master` 위로 rebase
- [ ] 빌드 통과 (`make` / `cmake --build`)
- [ ] 테스트 통과 (`make test` / `ctest`)
- [ ] 새 코드에 테스트 추가
- [ ] 경고 0, 새니타이저 통과 (프로젝트가 요구하면)
- [ ] 스타일 일치 (`clang-format`)
- [ ] 커밋 메시지 규칙 준수
- [ ] 관련 이슈 번호 링크, 변경 이유 설명
- [ ] 문서/CHANGELOG 업데이트 (필요 시)

### 리뷰 대응
- 방어적으로 굴지 마세요. 리뷰어는 프로젝트 품질을 지키는 사람입니다.
- 지적에 동의하면 고치고, 이견이 있으면 **정중하게 근거**를 대세요.
- 수정은 새 커밋으로 올리고(리뷰가 뭘 봐야 하는지 명확), 머지 직전에 squash 하는 게 흔합니다.
- 응답이 며칠 걸릴 수 있습니다. 메인테이너는 대부분 자원봉사자입니다.

## 6. 첫 기여로 좋은 것들

- 문서 오타/오류 수정 (부담 적고 환영받음)
- `good first issue` / `help wanted` 라벨 이슈
- 컴파일러 경고 제거
- 테스트 커버리지 추가
- 정적 분석/새니타이저가 찾은 실제 버그 수정 (근거가 명확)
- 이식성 수정 (특정 플랫폼에서 빌드 깨짐)

**하지 마세요**: 요청 없는 대규모 리팩터링, 스타일만 바꾸는 PR, 아키텍처 재설계 제안을
코드로 먼저 던지기(먼저 이슈로 논의).

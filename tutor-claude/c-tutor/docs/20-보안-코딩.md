# 20. 보안 코딩

> 목표: C에서 CVE가 나는 대표 5가지 패턴을 **직접 재현**하고 방어 코드를 쓴다.
> 그리고 컴파일러 하드닝 옵션과 안전한 API.

C는 세상 인프라의 대부분(커널, libc, OpenSSL, DB, 브라우저 엔진)을 떠받칩니다.
그래서 C의 보안 버그는 곧 세상의 보안 버그입니다.

---

## 0. 초등학생 버전 비유

C의 보안 버그는 대부분 **"편지 봉투보다 긴 편지를 억지로 밀어 넣어서, 옆 봉투 내용까지
덮어쓰는 것"** 입니다. 공격자는 이 "삐져나옴"을 정교하게 설계해서, 프로그램이 다음에
읽을 "다음에 할 일" 주소까지 자기가 원하는 값으로 바꿉니다.

방어의 핵심은 하나: **"이 버퍼에 들어올 수 있는 최대 크기를 항상 알고, 검사한다."**

---

## 1. 스택 버퍼 오버플로우 (가장 고전)

```c
void vulnerable(const char *input) {
    char buf[64];
    strcpy(buf, input);          // input 이 64자 넘으면 스택을 침범 → 복귀 주소 덮어씀
}
```

공격: `input` 을 길게 + 특정 바이트 패턴으로 → 함수가 `return` 할 때 공격자 코드로 점프.

**방어**:
```c
void safe(const char *input) {
    char buf[64];
    snprintf(buf, sizeof buf, "%s", input);   // 항상 크기 명시 + '\0' 종단
    // 또는 크기를 인자로 받아 검사
}
```
- `gets()` — **표준에서 삭제됨**. 절대 쓰지 마라.
- `strcpy`/`strcat`/`sprintf`/`scanf("%s")` — 크기 제한 없음. `strn*`/`snprintf`/`scanf("%63s")`.
- 컴파일러: `-fstack-protector-strong` (스택에 카나리 값을 심어 복귀 전 검사),
  `-D_FORTIFY_SOURCE=2 -O2` (컴파일 타임에 크기 아는 `memcpy`/`strcpy` 를 검사판으로 교체).

`./bin/20_overflow` (ASan으로 빌드 권장)가 스택/힙 오버플로우를 보여 줍니다.

## 2. 정수 오버플로우 → 할당 크기 조작

```c
void *make_array(size_t n, size_t elem) {
    return malloc(n * elem);      // n * elem 이 오버플로우하면 아주 작은 버퍼가 할당됨!
}                                 // 이후 n 개를 쓰면 힙 오버플로우

// 방어:
if (elem != 0 && n > SIZE_MAX / elem) return NULL;   // 곱셈 전에 검사
return malloc(n * elem);
// 또는 calloc(n, elem) — 내부에서 이 검사를 해 줌
```

- 길이 계산에 외부 입력이 들어가면 **항상** 오버플로우를 의심하세요.
- `-fsanitize=undefined` 로 부호 있는 오버플로우 탐지, 부호 없는 건 직접 검사.

`./bin/20_intoverflow` 참고.

## 3. 포맷 스트링 취약점

```c
printf(user_input);              // 위험! user_input 에 "%s%s%s%n" 이 있으면?
                                 // %n 은 "지금까지 출력한 바이트 수를 이 주소에 쓴다" → 메모리 쓰기
// 올바름:
printf("%s", user_input);        // 사용자 입력은 항상 인자로, 형식은 항상 리터럴로
```

- 컴파일러: `-Wformat -Wformat-security` (이 코스 `-Wall` 에 일부 포함).
- 규칙: **형식 문자열은 절대 변수/사용자 입력이 아니다.** 리터럴만.

---

## 4. Use-After-Free / Double-Free (8장 복습, 보안 관점)

- UAF는 단순 크래시가 아니라 **강력한 익스플로잇 프리미티브**입니다. 해제된 청크를
  공격자가 재할당해 내용을 제어하면, 원래 코드가 그걸 "유효한 객체"로 믿고 함수 포인터를 호출.
- 방어: `free(p); p = NULL;`, 소유권 명확화, 스마트한 할당자(`hardened_malloc`),
  ASan(개발), `-fsanitize=address` CI.

## 5. TOCTOU와 명령어 주입

```c
// TOCTOU (Time-Of-Check to Time-Of-Use)
if (access("/tmp/file", W_OK) == 0) {   // 검사
    fp = fopen("/tmp/file", "w");        // 사용 — 그 사이 심볼릭 링크로 바뀔 수 있음
}
// 방어: 검사하지 말고 바로 열고 실패를 처리. O_NOFOLLOW, openat 사용.

// 명령어 주입
char cmd[256];
snprintf(cmd, sizeof cmd, "convert %s out.png", filename);  // filename = "; rm -rf ~"
system(cmd);                                                 // 재앙
// 방어: system()/popen() 대신 execve() 로 인자 배열 직접 전달 (셸을 안 거침)
```

## 6. 입력 파싱 = 공격면

- 길이를 먼저 읽는 포맷(`[len][data]`)에서 `len` 을 **믿지 마라**. `len > 남은 바이트` 검사.
- 재귀 파서는 **깊이 제한**을 두어라 (스택 오버플로우 DoS).
- 정수 파싱은 `strtol` + 범위 검사 (12장).
- 신뢰 경계를 명확히: "이 데이터는 어디서 왔고, 검증됐는가?"

## 7. 하드닝 빌드 플래그 (실무 릴리스에 넣는 것)

```bash
cc -O2 \
   -D_FORTIFY_SOURCE=2 \          # libc 함수에 크기 검사 삽입 (-O1 이상 필요)
   -fstack-protector-strong \      # 스택 카나리
   -fPIE -pie \                    # 위치 독립 실행 파일 (ASLR 강화)
   -Wl,-z,relro,-z,now \           # GOT를 읽기 전용으로 (Linux)
   -Wl,-z,noexecstack \            # 스택 실행 금지
   -fcf-protection \               # CET (간접 분기 보호, x86)
   prog.c -o prog

# 개발/CI 에서는 추가로:
cc -g -O1 -fsanitize=address,undefined -fno-sanitize-recover=all ...
```

확인: `checksec --file=prog` (Linux), `otool -hv prog` (macOS).

## 8. 요약 규칙 (붙여 두세요)

1. 버퍼에 쓸 땐 **항상 크기를 알고 검사**. `snprintf` > `strn*` > `str*`.
2. 형식 문자열은 **리터럴만**.
3. 할당 크기 계산에 곱셈이 있으면 **오버플로우 검사** (또는 `calloc`).
4. `free` 후 `= NULL`. 소유권을 문서화.
5. 외부 입력의 길이/개수/오프셋을 **믿지 말고 검증**.
6. `system`/`popen`/`gets` 를 쓰지 마라.
7. 개발 내내 ASan/UBSan. CI에서 정적 분석 + 새니타이저 테스트.
8. `const` 를 최대한 쓰고, 경고를 `-Werror` 로.

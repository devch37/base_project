# 17. 디버깅·새니타이저·프로파일링

> 목표: 크래시를 만났을 때 **실무자가 실제로 하는 절차**. `lldb`/`gdb` 기본기,
> ASan/UBSan/MSan, Valgrind, 그리고 성능 프로파일링.

---

## 0. 초등학생 버전 비유

프로그램이 죽었어요. 탐정이 되어야 합니다.
- **디버거(`lldb`/`gdb`)** = 현장을 슬로우모션으로 되감아 보는 CCTV. "죽기 직전에 뭘 했지?"
- **새니타이저(ASan 등)** = 지문 감식반. "여기서 규칙을 어겼고, 그 원인은 3분 전 저 코드."
- **Valgrind** = 가상 세계에서 프로그램을 통째로 재현하며 모든 메모리 접근을 감시.
- **프로파일러** = 스톱워치. "시간을 어디서 다 썼지?"

---

## 1. 크래시 대응 절차 (외우세요)

```
1. 재현한다        — 최소 입력으로 항상 죽게 만든다
2. 도구를 켠다      — cc -g -fsanitize=address,undefined  (거의 항상 이걸로 원인이 나옴)
3. 스택 트레이스    — 죽은 줄 + 호출 경로를 읽는다
4. 값을 본다        — 그 지점에서 포인터/인덱스/크기를 출력하거나 디버거로 확인
5. 가설 → 수정 → 검증  — 새니타이저가 깨끗해질 때까지
6. 회귀 테스트 추가  — 같은 버그가 다시 나면 CI가 잡도록
```

**90%는 2번에서 끝납니다.** 디버거는 "논리 버그"(크래시는 안 나는데 결과가 틀림)에 주로 씁니다.

## 2. `lldb` (macOS 기본) / `gdb` (Linux) 최소 명령

```bash
cc -g -O0 examples/17/17_crash.c -o bin/17_crash
lldb ./bin/17_crash          # gdb ./bin/17_crash
```

| 하고 싶은 것 | lldb | gdb |
|---|---|---|
| 실행 | `run` (`r`) | `run` |
| 인자 주고 실행 | `run arg1 arg2` | `run arg1 arg2` |
| 죽은 지점 확인 | (자동 멈춤) `bt` | `bt` |
| 스택 프레임 이동 | `frame select 2` (`f 2`) | `frame 2` |
| 변수 값 | `p myvar` / `v` (지역 전체) | `print myvar` / `info locals` |
| 중단점 | `b main.c:42` / `b myfunc` | `break main.c:42` |
| 한 줄 실행 | `next` (`n`) / `step` (`s`) | `next` / `step` |
| 계속 | `continue` (`c`) | `continue` |
| 메모리 덤프 | `x/16xb ptr` | `x/16xb ptr` |
| watchpoint (값 변경 시 멈춤) | `watchpoint set variable x` | `watch x` |
| 종료 | `quit` | `quit` |

### 코어 덤프에서 사후 분석

```bash
ulimit -c unlimited                 # 코어 덤프 활성화 (Linux)
./bin/17_crash                      # 죽으면 core 파일 생성
gdb ./bin/17_crash core             # 죽은 순간의 상태로 열림
(gdb) bt full                       # 전체 스택 + 지역 변수
# macOS: 크래시 리포트는 ~/Library/Logs/DiagnosticReports/ 또는 lldb -c /cores/core.PID
```

`./bin/17_crash` 는 NULL 역참조로 일부러 죽습니다. 디버거로 열어 `bt` 를 연습하세요.

## 3. 새니타이저 (컴파일 타임에 계측 삽입)

| 새니타이저 | 플래그 | 잡는 것 | 비용 |
|---|---|---|---|
| **ASan** | `-fsanitize=address` | 힙/스택/전역 오버플로우, UAF, double free, (Linux) 누수 | ~2배 느림, ~3배 메모리 |
| **UBSan** | `-fsanitize=undefined` | 정수 오버플로우, 널 역참조, 정렬 위반, 잘못된 시프트 등 | 낮음 |
| **MSan** | `-fsanitize=memory` | 초기화 안 한 메모리 읽기 (Clang, Linux 전용, libc도 계측 필요) | ~3배 |
| **TSan** | `-fsanitize=thread` | 데이터 레이스 (19장) | ~5-15배 |

```bash
cc -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer prog.c -o prog
./prog        # 문제가 있으면 정확한 파일:줄 + 할당/해제 스택까지 출력

# 이 코스:
make asan  NAME=07_overflow
make ubsan NAME=16_ub_overflow
```

### ASan 출력 읽는 법 (예: heap-use-after-free)

```
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x...
READ of size 4 at 0x... thread T0
    #0 ... in main bugs.c:28          ← 잘못 접근한 곳
freed by thread T0 here:
    #0 ... in free
    #1 ... in main bugs.c:27          ← 언제 free 했는지
previously allocated here:
    #0 ... in malloc
    #1 ... in main bugs.c:25          ← 언제 할당했는지
```

세 개의 스택(접근/해제/할당)을 주면 대부분 즉시 원인이 보입니다.

**실무**: CI에서 테스트를 `-fsanitize=address,undefined` 로도 한 번 더 돌립니다.
릴리스 빌드엔 넣지 않습니다(성능 + ASan 자체가 공격면).

## 4. Valgrind (Linux; Apple Silicon 미지원 → macOS는 ASan/`leaks`)

```bash
valgrind --leak-check=full --track-origins=yes --error-exitcode=1 ./prog
```

- 재컴파일 불필요(바이너리를 가상 CPU에서 실행). 느림(10-30배).
- `memcheck`: 누수, 초기화 안 한 값, 잘못된 read/write.
- `--track-origins=yes`: 초기화 안 한 값이 "어디서 왔는지"까지 추적.
- macOS: `leaks --atExit -- ./prog` (이 코스 `make leaks NAME=...`).

## 5. 정적 분석 (컴파일러가 실행 없이)

```bash
cc -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wcast-qual -Wwrite-strings   # 기본
cc --analyze  (clang static analyzer)      # 경로 기반 분석
scan-build make                            # 빌드 전체를 분석
clang-tidy prog.c --                       # 린트 규칙
cppcheck --enable=all prog.c
```

CI에 `-Werror` + `scan-build` 를 넣으면 버그가 머지 전에 걸립니다.

## 6. 프로파일링

```bash
# 1) 어디가 느린가 — 샘플링 프로파일러
perf record ./prog && perf report          # Linux
# macOS: Instruments, 또는  sample <pid>,  또는  xctrace

# 2) 함수별 호출/시간 — 계측
cc -pg prog.c -o prog && ./prog && gprof prog gmon.out

# 3) 캐시 미스 / 분기 예측 실패
perf stat ./prog
valgrind --tool=cachegrind ./prog

# 4) 간단한 마이크로벤치 — 직접
clock_gettime(CLOCK_MONOTONIC, &t0); work(); clock_gettime(CLOCK_MONOTONIC, &t1);
```

원칙:
- **측정 전에 추측하지 마라.** 병목은 거의 항상 예상과 다릅니다.
- `-O2` (또는 `-O3`)로 빌드해서 측정. `-O0` 프로파일은 의미 없음.
- 알고리즘 > 상수배. O(n²)를 O(n log n)로 바꾸는 게 캐시 튜닝보다 큽니다.
- 그다음이 메모리 접근 패턴(연속성), 그다음이 분기, 마지막이 명령 수.

`./bin/17_profile` 이 `clock_gettime` 으로 "연속 배열 합" vs "연결 리스트 합"의
캐시 효과 차이를 보여 줍니다.

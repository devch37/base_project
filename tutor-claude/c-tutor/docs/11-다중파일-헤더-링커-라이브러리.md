# 11. 다중 파일·헤더·링커·라이브러리

> 목표: **선언 vs 정의**, 헤더에 무엇을 넣나, `static`/`extern` 의 링크(linkage),
> 컴파일 단위(translation unit), 그리고 정적(`.a`)·동적(`.so`/`.dylib`) 라이브러리.

이 장의 예제는 **여러 파일**로 이루어집니다: `examples/11/` 참고. `make 11` 로 빌드.

---

## 0. 초등학생 버전 비유

큰 요리책을 여러 명이 나눠 씁니다.
- 각자 자기 챕터(`.c`)를 따로 씁니다 → 따로 인쇄(컴파일)합니다.
- 하지만 "3장에 나오는 소스 만들기 참고" 처럼 서로를 언급하려면, **목차(헤더 `.h`)** 가 필요합니다.
  목차에는 "이런 레시피가 존재한다"(선언)만 적고, 실제 조리법(정의)은 각 챕터에 있습니다.
- 마지막에 편집자(**링커**)가 모든 챕터를 묶고, "참고" 표시를 실제 쪽번호로 연결해 책 한 권으로 만듭니다.

## 1. 선언(declaration) vs 정의(definition)

| | 선언 | 정의 |
|---|---|---|
| 함수 | `int add(int, int);` | `int add(int a, int b) { return a+b; }` |
| 변수 | `extern int g;` | `int g;` (또는 `int g = 5;`) |
| 개수 | 여러 번 해도 됨 | **딱 한 번** (One Definition Rule) |
| 위치 | 헤더 (`.h`) | 소스 (`.c`) |

- **헤더에 함수 정의를 넣으면?** 그 헤더를 include한 모든 .c에 정의가 복사됨 →
  링크 시 `duplicate symbol` 에러. (예외: `static inline`, `inline`, 매크로)
- **헤더에 `int g;` (정의)를 넣으면?** 여러 .c가 include하면 전역 변수가 여러 개 →
  링크 에러 또는 (구buggy) 조용한 병합. 헤더엔 `extern int g;` 만.

### 헤더에 넣는 것 / 안 넣는 것

| 헤더 (`.h`) | 소스 (`.c`) |
|---|---|
| 함수 **선언**(프로토타입) | 함수 **정의** |
| `typedef`, `struct`/`enum` 정의, 매크로 | `static` 헬퍼 함수 |
| `extern` 전역 변수 선언 | 전역 변수 **정의** |
| `static inline` 작은 함수 | 큰 로직 |
| 헤더 가드 필수 | — |

## 2. 컴파일 단위(Translation Unit)와 링크

```
counter.c  --전처리+컴파일-->  counter.o  ┐
strutil.c  --전처리+컴파일-->  strutil.o  ├--링크-->  프로그램
main.c     --전처리+컴파일-->  main.o     ┘   (+ libc)
```

- 각 `.c` + 그것이 include한 헤더들 = **하나의 컴파일 단위**. 서로 독립적으로 컴파일됨.
- 그래서 `main.c` 에서 `add()` 를 쓰려면 **선언**이 필요합니다(컴파일 시점엔 `add.c` 를 못 봄).
- 링커가 `.o` 들을 모아 심볼(함수/전역변수 이름)의 **정의를 찾아 주소를 연결**합니다.

### 대표 링크 에러

```
undefined symbol: add          → 선언은 했는데 정의(.o/라이브러리)를 안 줌. 오타/파일 누락/-l 누락
duplicate symbol: g            → 같은 심볼이 두 번 정의됨. 헤더에 정의를 넣었거나 static 을 안 붙임
```

## 3. `static` 과 `extern` — 링크(linkage) 결정

```c
// util.c
static int helper(void) { ... }   // internal linkage: 이 파일 안에서만. 다른 파일의 helper 와 무관
int g_count = 0;                   // external linkage: 다른 파일에서 extern 으로 접근 가능
static int s_cache = 0;            // internal linkage 전역: 이 파일 전용 상태

// util.h
extern int g_count;                // "정의는 다른 데 있다"

// main.c
#include "util.h"
g_count++;                         // OK, 링커가 util.o 의 g_count 로 연결
```

- **모든 헬퍼 함수/파일 전용 전역에 `static` 을 붙이세요.** 안 붙이면 이름이 전역에 노출되어
  다른 라이브러리와 충돌하고, 링커가 더 느려지고, API가 오염됩니다.
- 전역 가변 상태는 최소화. 필요하면 `static` + 접근 함수로 감싸세요.

## 4. 불투명 포인터로 모듈 캡슐화 (예제의 핵심)

`examples/11/counter.h` 는 `struct Counter` 의 **이름만** 공개합니다.
`counter.c` 만 내부 필드를 압니다. `main.c` 는 포인터로만 다룹니다.

```c
// counter.h
typedef struct Counter Counter;      // 불완전 타입
Counter *counter_new(long start);
void     counter_add(Counter *, long delta);
long     counter_value(const Counter *);
void     counter_free(Counter *);    // 소유권: new 로 받은 건 free 로 돌려준다
```

내부 구조를 `{ long value; }` 에서 `{ long value; long history[10]; }` 로 바꿔도
`main.c` 는 재컴파일조차 필요 없습니다(ABI 유지 시). 이게 실무 라이브러리 설계의 기본입니다.

## 5. 라이브러리 만들기

### 정적 라이브러리 (`.a`) — 링크 시 실행 파일에 복사됨

```bash
cc -c -O2 counter.c strutil.c            # counter.o strutil.o
ar rcs libmini.a counter.o strutil.o     # 아카이브(그냥 .o 묶음 + 색인)
cc main.c -L. -lmini -o app              # -L: 경로, -l mini: libmini.a 를 찾음
```

### 동적 라이브러리 (`.so` 리눅스 / `.dylib` macOS) — 실행 시 로드됨

```bash
cc -c -fPIC counter.c strutil.c          # -fPIC: 위치 독립 코드
cc -shared counter.o strutil.o -o libmini.so
cc main.c -L. -lmini -o app
LD_LIBRARY_PATH=. ./app                  # 실행 시 .so 를 찾을 경로 (macOS 는 DYLD_LIBRARY_PATH)
```

| | 정적 `.a` | 동적 `.so`/`.dylib` |
|---|---|---|
| 배포 | 실행 파일 하나로 끝 | `.so` 도 함께 배포/설치 필요 |
| 메모리 | 프로세스마다 코드 복사 | 여러 프로세스가 공유 |
| 업데이트 | 재링크 필요 | `.so` 만 교체 (ABI 호환 시) |
| 시작 속도 | 빠름 | 로더가 심볼 해석 (약간 느림) |

`make 11` 이 정적 라이브러리를 만들어 링크하는 과정을 보여 줍니다 (`examples/11/README.md`).
`pkg-config`, `rpath`, 심볼 버전 관리는 18장에서 다룹니다.

## 6. 초기화 순서와 `main` 이전

- 서로 다른 컴파일 단위의 전역 변수 초기화 순서는 **정해져 있지 않습니다**(C++ static init fiasco의 C판).
  전역이 다른 전역에 의존하게 만들지 마세요. `init()` 함수를 명시적으로 호출하세요.
- 전역은 **상수 표현식**으로만 초기화 가능: `int a[] = {1,2,3};` OK, `int x = f();` ✗ (파일 스코프).

## 7. 실습

1. `examples/11/` 를 `cc -c` 로 각각 컴파일하고 `nm *.o` 로 `U`(미정의)/`T`(정의된 함수) 심볼을 보세요.
2. `counter.c` 의 `counter_add` 에서 `static` 을 뗀 헬퍼를 만들고, `main.c` 에서 같은 이름 함수를
   정의해 `duplicate symbol` 을 재현한 뒤 `static` 으로 고치세요.
3. `libmini.a` 를 만들어 `main.c` 와 링크하세요. `ar t libmini.a` 로 내용을 확인하세요.
4. `counter` 의 내부 구조체에 필드를 추가해도 `main.o` 재컴파일 없이 재링크만으로 동작하는지 확인하세요.
5. 헤더에 `int g = 0;` (정의)를 넣고 두 .c 에서 include 해 링크 에러를 재현, `extern` 으로 고치세요.

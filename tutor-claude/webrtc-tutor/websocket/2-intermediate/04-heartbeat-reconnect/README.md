## 1. 반쯤 죽은 연결 (half-open connection)

TCP 는 상대가 **정상적으로 FIN/RST 를 보내야만** 끊김을 압니다. 하지만 현실은:

| 상황 | 서버가 보는 것 |
|---|---|
| 와이파이 → LTE 전환 (IP 변경) | 아무 패킷도 안 옴. 연결은 그대로 "ESTABLISHED" |
| 노트북 뚜껑 닫음 / 앱이 백그라운드에서 OS 에 의해 동결 | 동일 |
| 지하철 터널 / 엘리베이터 | 동일 |
| NAT/방화벽이 유휴 연결 매핑을 삭제 (보통 30~300초) | 서버→클라 패킷은 조용히 버려짐 |
| LB/프록시의 idle timeout (ALB 60초, Nginx 60초) | LB 가 연결을 끊지만 앱 서버는 모를 수 있음 |

서버가 아무것도 안 하면 이런 연결은 **수 분~수 시간(TCP keepalive 기본 2시간!)** 살아 있습니다.
그 결과 **접속자 수 거짓, 방 멤버 유령, 메모리/FD 누수, 죽은 소켓으로의 전송 낭비**가 생깁니다.

## 2. 서버 측: ping/pong 하트비트

```ts
setInterval(() => {
  for (const ws of wss.clients) {
    if (!isAlive.get(ws)) { ws.terminate(); continue; }   // 지난 라운드에 pong 없음 → 죽었다
    isAlive.set(ws, false);
    ws.ping();                                            // 이번 라운드에 pong 이 오면 true 로 복귀
  }
}, intervalMs);
```

* **`terminate()` vs `close()`**: `close()` 는 상대와 close 핸드셰이크가 필요한데, 상대가 죽었으니 응답이 안 옵니다.
  `terminate()` 는 소켓을 즉시 파괴합니다. *죽은 연결 정리에는 terminate*, *정상 종료에는 close*.
* **감지 시간 = 최대 2 × interval.** interval 이 30초면 최악 60초 뒤에 정리됩니다.
* **간격은 LB idle timeout 의 절반 이하로.** ALB 기본 60초라면 ping 은 20~30초 간격. 하트비트는 *죽은 연결 감지* 뿐 아니라 **LB 가 "활동 있음"으로 보게 해서 연결을 살려 두는** 역할도 합니다.
* 어떤 메시지든 받으면 `isAlive = true` — 데이터가 오고 있는데 pong 이 늦었다고 끊으면 오판입니다(바쁜 연결 오탐 방지).

### 비용
연결 N개 × 매 interval ping = 초당 N/interval 패킷. 100만 연결 / 30초 = 초당 3.3만 ping. 가볍지만 공짜는 아닙니다.
**ping 을 한꺼번에 보내지 말고** 연결별로 시작 시각을 분산(위상 분산)하면 CPU 스파이크를 줄일 수 있습니다.

## 3. 프로토콜 ping vs 앱 레벨 ping

| | 프로토콜 ping/pong (opcode 9/10) | 앱 레벨 ping (JSON 메시지) |
|---|---|---|
| 누가 보낼 수 있나 | 서버 (브라우저 JS 는 **불가**) | 양쪽 |
| pong 은? | 브라우저가 **자동** 응답 | 우리 코드가 응답 |
| 감지하는 것 | TCP/프로토콜 수준 생존 | **앱 수준 생존** (이벤트 루프가 막힌 서버/클라이언트도 감지) |
| RTT 측정 | 어려움 | `t` 타임스탬프 에코로 쉽게 |
| 프록시 호환 | 일부 프록시는 제어 프레임을 "활동"으로 안 봄 | 데이터 프레임이라 확실 |

**실무는 둘 다 씁니다.** 서버는 프로토콜 ping 으로 좀비를 치우고, 클라이언트는 앱 레벨 ping 으로 "서버가 죽었나"를 판단해 *빨리 재연결*합니다.
(브라우저는 `onclose` 가 TCP 타임아웃까지 안 올 수 있으므로, 클라이언트가 직접 5~10초 안에 pong 이 없으면 소켓을 버리고 새로 연결하는 것이 UX 에 중요합니다. → `WsClient.onPongTimeout`)

## 4. 재연결의 3원칙

### ① 지수 백오프 (Exponential Backoff)
실패할수록 기다림을 늘립니다: `0.5s → 1s → 2s → 4s → … → 상한(30s)`.
서버가 과부하/장애일 때 클라이언트가 고정 주기로 두드리면 *복구를 방해*합니다.

### ② 지터 (Jitter) — 가장 많이 빠뜨리는 것
서버가 재시작되면 **수만 클라이언트가 같은 순간** 끊깁니다. 백오프만 있으면 모두가 `2s, 6s, 14s` 후에 *동시에* 몰려옵니다(thundering herd).
서버는 막 살아났는데 다시 쓰러지고, 또 같은 주기로 반복됩니다.

`npx tsx websocket/2-intermediate/04-heartbeat-reconnect/jitter-simulation.ts` 결과(클라이언트 10,000명):

```
지터 없음  : 2.0s 구간에 10000건 (한 방에 몰림)
Full Jitter: 0~2s 에 고르게 퍼져 가장 몰린 구간 ≈ 1900건 (약 5배 완화) 이후도 평탄
```

| 지터 방식 | 대기 시간 | 특징 |
|---|---|---|
| none | `cap` | 쓰나미 |
| **full** | `random(0, cap)` | 가장 고르게 분산. 가끔 거의 0 에 가까운 대기가 나옴 |
| equal | `cap/2 + random(0, cap/2)` | 최소 대기 보장 + 분산 |
| decorrelated | `min(max, random(base, prev*3))` | 이전 대기에 의존. 경합이 심한 환경에서 우수 |

### ③ "성공"의 정의
TCP/WS 연결이 열렸다고 백오프를 초기화하면 안 됩니다. **인증에 실패해 곧바로 끊기는 서버**라면 `open → close → open → close` 를 *0 지연*으로 무한 반복하게 됩니다.
**서버가 받아 주었다는 신호(welcome 메시지 수신)** 를 받은 뒤에 카운터를 초기화하세요. (`WsClient` 가 이렇게 합니다)

## 5. close code 로 재연결 여부 결정

모든 끊김이 재연결 대상은 아닙니다.

| close code | 의미 | 재연결? |
|---|---|---|
| 1000 | 정상 종료 (보통 우리가 먼저 `close()` 함) | ✗ |
| 1001, 1006 | 서버 종료/네트워크 단절 | ✓ (백오프) |
| 1012, 1013 | 서버 재시작/과부하 | ✓ (서버가 알려 준 지연 + 지터) |
| 4001 인증 실패 | 재시도해도 소용없음 | ✗ → 로그인 화면으로 |
| 4002 토큰 만료 | **새 토큰으로** 재연결 | ✓ (URL 을 함수로 받아 매번 새 ticket 발급) |
| 4003 KICKED (중복 로그인) | 재연결하면 서로 쫓아내는 **핑퐁**이 생김 | ✗ |

## 6. 재연결 후에 해야 할 일 ("상태 복구")

서버 상태(방 멤버십, 구독)는 **연결과 함께 사라집니다.** 새 연결은 "처음 보는 클라이언트"입니다.

1. **방 재입장** — `WsClient` 는 `joinRoom` 한 방들을 기억했다가 자동 재입장합니다.
2. **놓친 메시지 복구** — 끊긴 사이의 메시지는 유실됩니다 → 7장(seq + resume).
3. **오프라인 큐** — 끊긴 동안 보낸 메시지를 쌓았다가 재전송할 수 있지만, 오래된 *상태성* 메시지(예: 이동 중 좌표)를 뒤늦게 쏟아내면 해롭습니다. 선택적으로 사용하세요.
4. **브라우저 이벤트 활용** — `online`/`offline`, `visibilitychange` 에서 즉시 재연결을 시도하면 UX 가 좋아집니다. 단 이때도 지터를 유지하세요.

## 7. 모바일/브라우저 특이사항 (심화)

* **탭이 백그라운드로 가면** 브라우저가 타이머를 1초 이상으로 늦추고(throttling), 15분+ 방치 시 *동결(Discard/Freeze)* 합니다. ping 타이머를 믿지 말고 `visibilitychange` 에서 연결 상태를 재확인하세요.
* **iOS Safari**: 앱 전환 시 소켓이 조용히 죽는 일이 흔합니다. 포그라운드 복귀 시 즉시 앱 ping 으로 확인.
* **서버 → 클라이언트 "곧 종료됩니다" 알림**(`server.shutdown` + `reconnectAfterMs`)은 배포 시 재접속 쓰나미를 분산하는 강력한 도구입니다 → 9장.

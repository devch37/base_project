## 1. 왜 WebSocket 인증은 따로 생각해야 할까?

브라우저의 `new WebSocket(url)` 에는 **커스텀 헤더를 붙일 방법이 없습니다.** `Authorization: Bearer …` 를 못 쓰죠.
그래서 후보가 이렇게 갈립니다.

| 방식 | 방법 | 장점 | 단점 / 위험 |
|---|---|---|---|
| **쿠키** | 같은 사이트면 자동 전송 | 구현 간단 | **CSWSH 위험** → Origin 검사 필수. 크로스 도메인(앱/타 사이트) 불리 |
| **URL 쿼리 토큰** | `?token=` | 간단, 도메인 무관 | **URL 이 프록시/액세스 로그/브라우저 히스토리에 남음** → 수명이 긴 JWT 를 넣으면 유출 위험 |
| **ticket (이 장)** | HTTP 로 단기 1회용 티켓 발급 → `?ticket=` | URL 에 남아도 이미 소비/만료 | 발급 API 한 번 더 호출 |
| **첫 메시지 인증** | 연결 후 첫 메시지로 토큰 | URL 에 안 남음 | 인증 전 연결이 열려 있음(자원 점유·DoS), 서버 로직 복잡 |
| **서브프로토콜 헤더** | `new WebSocket(url, ['bearer', token])` | 로그에 덜 남음 | 편법. 표준 의도와 다름 |

**권장(ticket)**: HTTP API 인증(쿠키 or Bearer)은 이미 안전하게 구현되어 있으니 *그것으로* 30초짜리 1회용 티켓을 받고, 그 티켓으로만 WebSocket 을 엽니다.
티켓이 URL 에 노출돼도 **30초 안에 한 번**만 유효해서 실질 위험이 거의 없습니다.

## 2. CSWSH — WebSocket 이 CORS 의 보호를 못 받는다

```
사용자는 bank.com 에 로그인 중 (쿠키 보유)
           │
           ▼  사용자가 evil.com 방문
evil.com 의 스크립트:  new WebSocket('wss://bank.com/ws')
           │   브라우저가 bank.com 쿠키를 자동으로 붙여서 전송!
           ▼
bank.com 서버: "쿠키가 유효하네? 로그인된 사용자의 연결이구나" → 101
           │
evil.com 이 사용자의 권한으로 메시지를 보내고, 응답을 읽는다 (계정 탈취)
```

* **WebSocket 핸드셰이크는 동일 출처 정책/CORS 의 대상이 아닙니다.** (일반 XHR/fetch 와 다른 점)
* 방어의 핵심: 서버가 **`Origin` 헤더를 허용 목록과 대조**합니다. 브라우저는 `Origin` 을 항상 정확히 붙이고, **스크립트가 위조할 수 없습니다.**
* 쿠키가 아니라 ticket 방식이라면 evil.com 은 ticket 을 얻을 수 없지만(발급 API 가 CORS 로 보호), **Origin 검사는 여전히 방어를 겹겹이 하는 습관**입니다.
* Origin 이 없는 요청(서버-서버, CLI 도구)은 `allowNoOrigin` 정책으로 따로 결정합니다. *브라우저 전용 서비스라면 거절*하세요.
* `Origin: null`(샌드박스 iframe, `file://`)도 흔한 우회 입구입니다. 허용 목록에 `"null"` 을 넣지 마세요.

## 3. 업그레이드 시점에 거절하기 (왜 `noServer` 인가)

`new WebSocketServer({ port })` 는 편하지만 *연결을 맺은 뒤*에야 코드가 실행됩니다.
`noServer` + HTTP 서버의 `'upgrade'` 이벤트를 쓰면 **101 을 보내기 전에** 검사하고, 실패하면 **그냥 HTTP 오류**를 돌려줄 수 있습니다.

* 이득 1: 인증 실패 연결이 WebSocket 자원(버퍼, 하트비트, 메모리)을 **전혀 쓰지 않습니다**.
* 이득 2: 로드밸런서/모니터링에서 401/403 이 **일반 HTTP 지표로** 보입니다.
* 이득 3: 클라이언트(브라우저)는 거절 사유를 `onerror`/`onclose(1006)` 로만 알지만, 서버 로그엔 정확히 남습니다.

> ⚠ 브라우저 JS 는 업그레이드 거절의 **HTTP 상태코드를 읽을 수 없습니다.** 그냥 `close 1006` 로 보입니다.
> "인증 실패인지 네트워크 문제인지" 구분하려면 *연결 전에 ticket 발급 API 응답(401)로 먼저 판단*하는 것이 UX 상 낫습니다.
> (연결 후에 4001 같은 앱 close code 로 알리는 방식도 가능 — 일단 101 을 주고 즉시 close 4001)

처리 순서도 중요합니다: **싼 검사 → 비싼 검사**. 경로·Origin(문자열 비교) → 서명 검증(HMAC) → 저장소 조회(1회용).

## 4. ticket 설계 포인트 (`src/auth.ts`)

```
ticket = base64url(payload JSON) + "." + base64url( HMAC-SHA256(payload, secret) )
payload = { sub: "alice", exp: 1730000030, jti: "uuid" }
```

* **서명 검증은 상수 시간 비교**(`timingSafeEqual`). 일반 `===` 는 앞에서부터 비교하다 멈추므로 *얼마나 맞았는지*가 응답 시간으로 샙니다(타이밍 공격).
* **짧은 만료(30초)** + **1회용(`jti` 소비)**. 1회용 저장소는 *모든 서버가 공유*해야 합니다 — 서버가 여러 대면 Redis `SET jti 1 NX EX 60`.
* ticket 에 **권한(role)을 길게 담지 마세요.** 접속 시점에 DB 에서 최신 권한을 읽는 것이 안전합니다(권한이 바뀌어도 반영).
* 운영에서는 검증된 JWT 라이브러리(`jose`)와 **키 로테이션(`kid`)** 을 쓰세요. 이 구현은 원리를 보여 주는 최소판입니다.
* 비밀키는 환경변수/시크릿 매니저에서. **코드에 하드코딩 금지**(데모의 `dev-secret-change-me` 는 데모용).

## 5. 연결 이후의 방어

### 메시지 크기: `maxPayload`
`ws` 기본값은 **100MB** 입니다! 공격자가 한 메시지로 수백 MB 를 보내면 서버가 메모리에 버퍼링합니다.
용도에 맞게 작게(예: 64KB) 제한하세요. 초과하면 `ws` 가 자동으로 **1009** 로 연결을 닫습니다. (파일 전송 같은 큰 데이터는 별도 HTTP 업로드를 권장)

### 속도 제한 / 연결 수 제한 (6장·`src/ratelimit.ts`)
* 연결당 메시지 속도(토큰 버킷), **IP·사용자당 동시 연결 수** 제한.
* 인증 전 연결은 수명을 짧게(예: 5초 안에 인증 안 되면 종료) — 첫 메시지 인증 방식일 때 특히 필수.

### 연결 최대 수명 + 재인증
ticket 은 *접속 순간*만 증명합니다. 연결이 며칠씩 살면 그 사이 **사용자가 로그아웃/정지/권한 박탈**되어도 연결은 계속 유효합니다.
* 최대 수명(예: 1시간)이 지나면 4002 로 끊어 **재접속 때 다시 인증**하게 하고,
* 로그아웃/정지 이벤트가 오면 **그 사용자의 모든 연결을 즉시 종료**(4001)합니다. (다중 서버라면 이 "폐기 이벤트"를 Redis Pub/Sub 으로 전파 → 8장)

### 메시지 단위 인가
연결이 인증됐다고 *모든 메시지가 허용되는 것이 아닙니다.* `room.join`, `admin.kick` 등 **각 동작마다 권한을 검사**하세요(3장의 "방 멤버인가?" 검사).

### 출력 인코딩 (XSS)
채팅 메시지를 `innerHTML` 로 그리면 WebSocket 으로 들어온 `<script>` 가 실행됩니다. 서버가 검증해도 **클라이언트 렌더링에서 이스케이프**는 필수입니다.

### TLS 와 프록시 헤더
* 운영은 **반드시 `wss://`**. 평문이면 ticket 도 메시지도 스니핑됩니다.
* TLS 를 LB/Nginx 에서 종료한다면 `X-Forwarded-For`/`X-Real-IP` 로 **진짜 클라이언트 IP** 를 얻어 제한/로그에 쓰되, **신뢰할 프록시에서 온 헤더만** 믿으세요(그렇지 않으면 위조 가능).

# 06. 백프레셔와 속도 제한 — "느린 한 명이 서버를 죽이지 못하게"

> **한 줄 요약**: `ws.send()` 는 **즉시 리턴**합니다. 상대가 느리면 데이터는 **서버 메모리**에 쌓입니다. 한계선(soft/hard)·완료 콜백·병합(conflation)으로 서버를 지키고, 들어오는 쪽은 토큰 버킷으로 제한하세요.

|---|---|

| [`demo.ts`](./demo.ts) | `npm run ws:06` — 메모리 폭증을 직접 눈으로 + 방어 5가지 |
| 관련 구현 | [`src/connection.ts`](../../src/connection.ts) (soft/hard 한계), [`src/ratelimit.ts`](../../src/ratelimit.ts) (토큰 버킷) |

## 1. 문제: `send()` 가 느려지지 않는다

```
생산자(우리 코드) ──▶ [ ws 내부 큐 ──▶ 커널 송신 버퍼 ] ──▶ 네트워크 ──▶ 느린 클라이언트
                          ▲
                          └ 여기가 부푼다.  ws.bufferedAmount = 이 큐의 바이트 수
```

데모 ①의 결과:

```
1000번 send() 호출이 즉시 끝남. ws.bufferedAmount = 61.3MB / RSS 증가 ≈ 57MB
```

클라이언트가 읽지 않는 *한 명*이 서버 메모리를 57MB 붙잡았습니다. 접속자 1000명 중 5%가 모바일 터널에 들어가 있다면? Node 힙/RSS 가 부풀고, GC 가 길어지고, 결국 OOM 으로 **모든 사용자**가 영향을 받습니다.

> **흔한 사고 패턴**: 방(room) 브로드캐스트에서 느린 클라이언트 몇 명 때문에 서버 전체 응답 지연이 늘다 컨테이너 메모리 한도에서 OOMKilled → 재시작 → 모든 클라이언트 동시 재접속(쓰나미) → 또 OOM.

WebSocket(TCP) 에는 **애플리케이션 레벨 흐름 제어가 없습니다.** TCP 의 윈도우 제어는 커널 버퍼까지만 막아 줍니다.
그 위의 Node 큐는 우리 책임입니다.

## 2. 방어 전략 4가지 — 메시지 성격에 맞게 고른다

| 메시지 성격 | 예 | 전략 | 코드 |
|---|---|---|---|
| **버려도 되는** (다음 값이 곧 덮어씀) | 마우스 커서, 타이핑 중 표시, 통계 | **soft 한계 초과 시 건너뛰기** | `guardedSend({lossy:true})` |
| **마지막 값만 의미 있는** | 시세, 게임 상태, 센서 | **Conflation(병합)** — 키별 최신 값만 | `ConflatingSender` |
| **전부 보내야 하는 스트림** | 파일, 대용량 스냅샷, 로그 tail | **큐가 낮아질 때까지 대기하며 전송** | `streamWithBackpressure` |
| **누락되면 안 되는 개별 이벤트** | 주문 체결 알림 | 전송 큐를 두되 **한계 초과 시 연결을 끊고** 재연결 후 **resume** (7장) | `guardedSend` hard 한계 |

### hard 한계 = "서버 보호가 사용자 한 명의 경험보다 우선"
hard 한계를 넘으면 `close(4009, 'slow consumer')` 로 끊습니다. 클라이언트는 재연결해서 **놓친 부분을 resume** 으로 가져오거나 전체 상태를 다시 받습니다.
"끊으면 사용자가 불편하지 않나?" — 이미 못 받고 있던 사용자이고, 방치하면 다른 모든 사용자가 불편해집니다.

> **끊을 때도 주의**: `ws.close()` 는 close 프레임을 *송신 큐 뒤에* 줄 세웁니다. 큐가 가득 찬 느린 소비자는 close 프레임조차 못 받습니다. 그래서 일정 시간 뒤 `terminate()` 로 마무리합니다(`Connection.close(forceAfterMs)`).

### 한계값은 어떻게 정할까?
* soft: 평소 정상 클라이언트의 일시적 정체 허용 범위 (예: 1MB, 또는 수 초 분량의 트래픽)
* hard: soft 의 4배 정도. **(hard × 동시 접속 수)** 가 서버 메모리 예산을 넘지 않게 역산하세요.
  예) 메모리 예산 2GB, 접속 1만 → 연결당 평균 200KB. 모두가 hard 에 다다를 일은 없지만 *최악의 몇 %* 가 한계를 쓴다고 가정하고 여유를 둡니다.

## 3. `send()` 콜백과 `bufferedAmount`

```ts
ws.send(data, (err) => { /* 데이터가 소켓에 "써진" 뒤 호출. 느린 소비자면 늦게 호출됨 */ });
```

* 콜백을 `await` 하면 한 번에 하나씩 보내는 **자연스러운 백프레셔**가 됩니다. 다만 단순 직렬 전송은 처리량이 낮을 수 있으니, 큐 크기(`bufferedAmount`) 기준으로 *여러 개를 파이프라인*하는 것이 효율적입니다(데모 ③은 highWater 256KB).
* `bufferedAmount` 는 *브라우저*의 `WebSocket` 에도 있습니다. 클라이언트가 대용량을 보낼 때도 똑같이 확인하세요(WebRTC DataChannel 의 `bufferedAmountLowThreshold` 도 같은 원리 → webrtc 3장).

## 4. Conflation(병합) — 가장 우아한 해법

```
생산: btc=60001, btc=60002, btc=60003, …(초당 수천 건)     클라이언트는 느림
                          │
           [ 대기 슬롯: btc → 최신값 하나만 ]   ← 덮어쓰기
                          │ 소켓이 한가할 때만
                          ▼
              { btc: 60098, eth: 3098, sol: 248 }  한 메시지로 묶어서 전송
```

데모 ④: 갱신 ≈ 9800건 → 병합으로 9637건 흡수 → **실제 전송 58건**, 최종 값은 정확.
메시지 수가 줄 뿐 아니라 **헤더/직렬화 비용**도 줄어 CPU 가 절약됩니다. 소비자가 빨라지면 자동으로 다시 촘촘해집니다(적응형).
단점: **중간 값(히스토리)이 필요하면 못 씁니다**(예: 차트의 모든 틱, 감사 로그). 그런 경우는 스트리밍 + 백프레셔 전략.

## 5. 인바운드: 속도 제한 (Rate Limiting)

방향이 반대인 문제입니다. *클라이언트가* 서버를 폭주시키는 경우(버그 루프, 악의).

**토큰 버킷** (`src/ratelimit.ts`)
```
양동이(capacity=20) — 요청 1개 = 토큰 1개. 토큰은 초당 refill(10)개씩 충전.
버스트 20 까지 즉시 허용 → 이후 평균 초당 10 으로 제한.
```
* 연결당 O(1) 메모리(숫자 2개). 고정 윈도우 카운터는 경계에서 2배 버스트가 가능하고 구현이 번거롭습니다.
* **초과 시 정책**: 처음엔 `rate_limited` 에러 응답(클라이언트가 속도를 줄이도록) → **연속 위반이 N회를 넘으면 4008 로 종료**.
* **무엇을 제한할까**: 메시지 *개수*뿐 아니라 *바이트*, *방 입장 횟수*, *비싼 핸들러*(DB 쿼리 유발)는 더 낮게. 비용이 큰 메시지는 토큰 여러 개를 소비하게(`tryTake(5)`).
* **분산 환경**: 연결 단위 제한은 노드 로컬로 충분하지만, **사용자/IP 단위 전역 제한**은 Redis(`INCR`+`EXPIRE`, 또는 Lua 스크립트로 토큰 버킷)가 필요합니다.

### 연결 수 제한도
* 서버 전체 `maxConnections` 초과 시 `503 + Retry-After` 로 **빨리 거절**(load shedding).
* IP/사용자당 동시 연결 상한. (NAT 뒤 사무실 수백 명이 한 IP 일 수 있으니 *너무 낮게* 잡지 마세요)

## 6. 압축(`permessage-deflate`)과 메모리

* 연결마다 zlib 컨텍스트(수십~수백 KB)와 CPU 를 씁니다. 연결이 10만 개면 수 GB 가 될 수 있습니다.
* `ws` 의 `perMessageDeflate` 는 기본 **꺼짐(서버)** — 켜려면 `threshold`(작은 메시지는 압축 안 함), `concurrencyLimit`, 컨텍스트 재사용 옵션을 신중히.
* 작은 JSON 위주면 압축 이득이 작습니다. 대용량 텍스트(로그, 큰 JSON 스냅샷)일 때만 고려하세요.

## 7. 모니터링 포인트

| 지표 | 의미 | 경보 기준 예 |
|---|---|---|
| 연결당 `bufferedAmount` 분포 (p99) | 느린 소비자 비율 | p99 > soft 한계가 지속 |
| `dropped` / `slow_consumers` 카운터 | 방어가 작동한 횟수 | 급증 시 네트워크/클라이언트 이슈 |
| Node RSS / heap / event loop lag | 메모리·CPU 압박 | 이벤트 루프 지연 > 100ms |
| 브로드캐스트 팬아웃 시간 | 큰 방이 루프를 막는지 | 방 인원 증가 시 선형 증가 |

(`src/metrics.ts` 가 위 카운터를 Prometheus 형식으로 노출 → 9장)

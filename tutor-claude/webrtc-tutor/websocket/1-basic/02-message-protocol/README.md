# 02. 메시지 프로토콜 설계 — "연결만 있다고 서비스가 되진 않는다"

> **한 줄 요약**: WebSocket 은 *문자열/바이너리 파이프*일 뿐입니다. 메시지 **봉투(envelope)·버전·검증·에러 모델·요청/응답 상관관계**를 우리가 직접 설계해야 서비스가 됩니다.

| 파일 | 내용 |
|---|---|
| [`messages.ts`](./messages.ts) | zod 스키마 = 프로토콜 정의서 (검증 + 타입을 한 번에) |
| [`server.ts`](./server.ts) | 파싱 → 버전 확인 → 검증 → 타입별 라우팅 → 응답 |
| [`client.ts`](./client.ts) | `await call()` 을 가능하게 하는 상관관계 ID + 타임아웃 |
| [`demo.ts`](./demo.ts) | `npm run ws:02` |

---

## 1. 봉투(Envelope)가 필요한 이유

HTTP 에는 메서드/경로/헤더/상태코드가 있어 "무슨 요청인지, 어떤 응답인지"가 자연스럽게 구분됩니다.
WebSocket 에는 그런 게 **전혀 없습니다**. 그래서 모든 메시지에 이런 모양을 약속합니다.

```jsonc
{
  "v": 1,                  // 프로토콜 버전 — 훗날 호환성 깨질 때를 대비해 처음부터 넣는다
  "id": "c17",             // 요청 ID (응답을 기다리는 메시지만)
  "replyTo": "c17",        // 응답이면 어느 요청에 대한 것인지
  "type": "math.add",      // 라우팅 키. "도메인.행위" 네이밍을 추천
  "payload": { "a": 2, "b": 3 },
  "error": { "code": "bad_payload", "message": "..." }   // 에러 응답일 때
}
```

**설계 규칙**
1. `type` 은 **소문자 + 점 표기** (`room.join`, `signal.offer`). 서버 핸들러 맵의 키가 된다.
2. 에러도 같은 봉투로 — 클라이언트가 한 가지 방식으로 처리한다.
3. 에러 **`code`(기계용)** 와 **`message`(사람용)** 를 분리한다. 클라이언트 분기는 code 로만.
4. **서버가 채우는 필드**(발신자, 서버 시각, 순번)는 클라이언트가 보낸 값을 무시하고 덮어쓴다 → 사칭 방지 (다음 장들에서 `from`, `seq`).
5. 알 수 없는 필드는 **무시**한다(zod 기본 동작). 새 필드를 추가해도 구버전 클라이언트가 깨지지 않게(전방 호환).

## 2. 검증: "TypeScript 타입은 런타임에 사라진다"

```ts
ws.on('message', (data) => {
  const msg = JSON.parse(data.toString()) as Request;   // ❌ 거짓말. as 는 아무것도 검사하지 않는다
```

네트워크 너머의 데이터는 **무엇이든 올 수 있습니다**(버그 있는 클라이언트, 공격자). 그래서
`JSON.parse → zod.safeParse` 를 거쳐야만 "검증된 타입"이 됩니다. 이 장의 `messages.ts` 는 한 스키마에서

* 런타임 검증기 (`requestSchema.safeParse`)
* TypeScript 타입 (`z.infer`)

둘을 모두 얻어서 **타입과 검증이 어긋날 수 없게** 합니다. 핸들러 맵 타입(`Handlers`)은 `type` 별로 payload 타입이 정확히 좁혀지고,
새 메시지를 스키마에 추가하면 핸들러를 안 만들었을 때 **컴파일 에러**가 납니다.

### 파싱 실패는 "예외"가 아니라 "일상"
깨진 JSON, 모르는 type, 틀린 payload 는 공개 서비스에서 매초 일어납니다. 그래서 `safeParse`(예외 없음)로 결과 객체를 받고,
**에러 응답을 보낸 뒤 연결은 유지**합니다. (반복적으로 위반하면 속도 제한/종료 → 6장)

### 정보 노출 주의
* 서버 내부 예외 메시지(`e.message`, 스택)는 **절대 클라이언트로 보내지 않습니다**. 로그에만 남기고 `internal` 로만 응답.
* zod 에러의 전체 `issues` 는 스키마 구조를 드러냅니다. 첫 이슈의 경로/사유만 요약하는 정도가 적당합니다.

## 3. 요청/응답(RPC)을 WebSocket 위에 올리기

WebSocket 은 "메시지가 오면 이벤트가 터지는" 모델이라, 응답이 **요청 순서대로 도착한다는 보장이 없습니다**(서버 핸들러가 비동기이므로).
요청마다 고유 `id` 를 붙이고 응답에 `replyTo` 로 돌려받아 짝을 맞춥니다.

```
call('slow.work', 300ms) → id=c1 ──┐                        ┌── 응답 replyTo=c2 (50ms 뒤 먼저 도착)
call('slow.work',  50ms) → id=c2 ──┤  서버(동시 처리)  ──────┤
                                   └────────────────────────└── 응답 replyTo=c1 (300ms 뒤 도착)
```

클라이언트 구현의 필수 3요소 (`client.ts`)

| 요소 | 안 하면? |
|---|---|
| `pending` 맵 (id → resolve/reject) | 응답을 요청과 못 짝짓는다 |
| **요청 타임아웃** | 서버 버그/유실로 Promise 가 영원히 대기, 메모리 누수 |
| **연결 끊김 시 전부 reject** | 재연결 후에도 이전 요청이 영원히 안 끝남 |

> **멱등성(idempotency)**: 타임아웃이 났다고 서버가 실행하지 않았다는 뜻은 **아닙니다**(응답만 유실됐을 수 있음).
> 재시도해도 안전하려면 "결제"·"주문" 같은 요청은 서버가 **요청 ID 로 중복을 걸러야** 합니다 → 7장.

## 4. 서버 푸시와 요청/응답의 공존

같은 연결로 *응답*(`replyTo` 있음)과 *푸시*(`replyTo` 없음)가 섞여 옵니다. 클라이언트는 `replyTo` 유무로 분기합니다.
푸시는 `event.*` 처럼 네임스페이스를 구분해 두면 라우팅이 쉽습니다.

## 5. 직렬화 포맷 선택 (심화)

| 포맷 | 장점 | 단점 | 쓸 때 |
|---|---|---|---|
| **JSON** | 디버깅 쉬움(텍스트), 모든 언어 지원 | 크다, 바이너리(이미지/오디오) 표현이 비효율(base64 +33%) | **기본값**. 대부분의 메시지 |
| **MessagePack / CBOR** | JSON 호환 모델, 20~40% 작고 빠름 | 사람이 못 읽음 | 트래픽이 많은 실시간 상태 동기화 |
| **Protobuf / FlatBuffers** | 가장 작고 빠름, **스키마 진화 규칙** 내장 | 스키마/코드젠 필요 | 모바일·게임·대규모, 다언어 팀 |
| **원시 바이너리 프레임** | 최소 오버헤드 | 직접 설계/유지 | 오디오/비디오 청크, 파일 전송 |

실무 감각: **제어 메시지는 JSON, 대용량 데이터는 바이너리 프레임**으로 섞어 쓰는 경우가 많습니다. 바이너리 프레임은 앞 1~4바이트에 "종류 코드"를 두고 뒤에 데이터를 붙입니다.

### 기존 규격을 쓸 수도 있습니다
* **JSON-RPC 2.0** — `{jsonrpc:"2.0", method, params, id}`. 이 장의 envelope 과 거의 같은 아이디어의 표준.
* **graphql-ws** — GraphQL 구독용 서브프로토콜.
* **STOMP / MQTT over WebSocket** — 브로커 기반 pub/sub 규격. 이미 브로커(RabbitMQ, Mosquitto)가 있다면 유용.
* **Socket.IO** — 규격이 아니라 **자체 프로토콜을 가진 라이브러리**(룸, ack, 재연결, 폴백). 편하지만 순수 WebSocket 클라이언트와 **호환되지 않고**, 서버/클라이언트가 모두 Socket.IO 여야 합니다.
  → 이 튜토리얼이 `ws` + 직접 설계를 택한 이유: *원리를 배우고*, 필요한 기능만 골라 *가볍게* 쓰기 위해서입니다.

## 6. 버전 관리

`v` 를 처음부터 넣는 이유: 필드 이름을 바꾸거나 의미를 바꾸는 순간 **배포 중에 구/신 클라이언트가 공존**합니다(모바일 앱은 업데이트가 느리다!).
* 하위 호환 가능한 변경(필드 추가) → 버전 그대로.
* 깨는 변경 → `v: 2` 를 추가하고 서버가 **둘 다 처리**하거나, 구버전에 `unsupported_version` 으로 "업데이트 필요"를 알린다.
* 연결 시 서브프로토콜(`Sec-WebSocket-Protocol: myapp.v2`)로 버전을 협상하는 방법도 있습니다.

# 03. 방(Room)과 브로드캐스트 — "누구에게 보낼 것인가"

> **한 줄 요약**: 방 = *같은 메시지를 받는 연결들의 집합*. 두 방향의 인덱스(방→멤버, 연결→방), **끊김 시 정리**, **빈 방 삭제**, **권한 검사**가 핵심입니다.

| 파일 | 내용 |
|---|---|
| [`rooms.ts`](./rooms.ts) | `Rooms` 자료구조 (join / leave / leaveAll / broadcast) |
| [`server.ts`](./server.ts) | 방 입장·퇴장·발언·접속자 알림을 처리하는 채팅 서버 |
| [`client.ts`](./client.ts) | 출력이 보기 좋은 채팅 클라이언트 |
| [`demo.ts`](./demo.ts) | `npm run ws:03` |

---

## 1. 방 모델

```
rooms (방 → 멤버)                    joined (연결 → 소속 방)
 "lobby" → { alice, bob }            alice → { "lobby" }
 "dev"   → { carol }                 bob   → { "lobby" }
                                     carol → { "dev" }
```

* **방→멤버** 는 브로드캐스트(`for (m of rooms.get(room))`)용.
* **연결→방** 은 연결이 끊겼을 때 *어느 방들에서 빼야 하는지* 를 O(소속 방 수)로 알기 위한 역인덱스.
  이게 없으면 전체 방을 훑어야 합니다(O(전체 방 수)) — 연결이 수만 개일 때 끊김 이벤트마다 이러면 서버가 멈춥니다.
* 연결 객체에 `ws.rooms = ...` 처럼 속성을 직접 붙여도 되지만(5장 이후의 `Connection` 클래스가 이 방식),
  `WeakMap` 을 쓰면 **연결이 GC 될 때 자동으로 정리**되어 누수 위험이 줄어듭니다.

### 방은 "만들지" 않는다 — 첫 입장자가 만들고 마지막 퇴장자가 지운다
방을 미리 생성/삭제하는 API 를 두면 "방 목록과 실제 상태가 어긋나는" 버그가 생깁니다. **멤버십이 곧 방의 존재**가 되게 하세요.

## 2. 브로드캐스트

```ts
for (const ws of members) {
  if (ws === except) continue;           // 보낸 사람 제외 (UI 에서 자기 메시지는 로컬 에코로 보여 주는 게 보통)
  if (ws.readyState === ws.OPEN) ws.send(message);   // 이미 닫힌 소켓에 보내지 않기
}
```

**성능 포인트**
1. `JSON.stringify` 는 **한 번만** 하고 같은 문자열을 N명에게 보냅니다 (`for` 안에서 매번 직렬화하면 N 배 CPU).
2. 방 인원이 수천 명이면 `for` 루프 자체가 이벤트 루프를 오래 점유합니다. → 큰 방은 배치로 나눠 `setImmediate` 로 양보하거나, 아예 *방 단위로 별도 워커/노드*로 샤딩합니다(8장).
3. 순회 중 `leave` 가 일어나도 안전하도록(예: `send` 중 에러로 정리) **복사본을 순회**하거나 삭제 시점을 신중히 다룹니다. `leaveAll` 이 `[...]` 복사본을 쓰는 이유입니다.
4. **팬아웃(fan-out) 증폭**: 방 인원이 N, 초당 메시지가 M 이면 서버는 초당 **N×M** 번 전송합니다. 채팅방 1000명 × 초당 10메시지 = 초당 1만 전송. 이 곱셈이 서버 용량 계획의 핵심입니다.

## 3. 연결 끊김 처리 — 가장 흔한 버그의 원천

```ts
ws.on('close', () => { for (const room of rooms.leaveAll(ws)) broadcast(room, 퇴장 알림) });
```

* 사용자는 *브라우저 탭을 닫고*, *노트북 뚜껑을 덮고*, *엘리베이터에 들어가고*, *앱을 강제 종료*합니다.
  어떤 경우든 **서버의 `close` 이벤트가 정리의 유일한 기회**입니다. (단, 완전히 조용히 죽은 연결은 `close` 가 한참 뒤에 옵니다 → 4장 하트비트)
* 정리를 빼먹으면:
  * 유령 멤버가 방에 남아 **브로드캐스트가 계속 죽은 소켓으로** 가고
  * `Set` 이 연결 객체를 붙잡고 있어 **GC 가 안 되어 메모리가 새며**
  * 접속자 수/온라인 표시가 틀립니다.

> 데모의 `bob.ws.terminate()` 는 close 프레임 없이 TCP 를 즉시 끊습니다. 서버는 이 경우에도 `close`(code 1006) 이벤트를 받습니다.

## 4. 권한: "방에 들어 있나?"를 매번 확인

`say` 핸들러는 보낸 연결이 그 방의 멤버인지 검사합니다. 이걸 빼면 **방 이름만 알면 누구나 남의 방에 메시지를 쏠 수 있습니다.**
실무에서는 입장 시점에도 권한(초대/비밀번호/소유자 등)을 검사해야 합니다. 방 이름을 추측 불가능한 ID(UUID)로 만드는 것은 *보조 수단*일 뿐 인증이 아닙니다.

**입력 길이 제한**도 방어선입니다. 방 이름(64자)·닉네임(32자)·메시지(500자)를 자르지 않으면, 공격자가 거대한 방 이름을 수백만 개 만들어 메모리를 고갈시킬 수 있습니다.

## 5. 상태(State)는 어디에 둘까

이 장의 방/멤버십 정보는 **서버 프로세스 메모리**에 있습니다. 그 말은

* 서버를 재시작하면 모든 방이 사라지고(클라이언트가 재입장해야 함 → 4장 재연결에서 자동 재입장),
* **서버를 2대로 늘리면 서로의 방을 모릅니다.** 서버 A 의 alice 와 서버 B 의 bob 은 같은 방에 있어도 대화할 수 없습니다.

이 문제의 해결(공용 메시지 버스 + 공유 presence)이 **8장**의 주제입니다. 지금은 "상태를 메모리에 두면 단일 서버 한계가 생긴다"는 것만 기억하세요.

## 6. 방 단위 설계 패턴

| 패턴 | 설명 | 예 |
|---|---|---|
| **채널(방) 구독** | 클라이언트가 관심 있는 방만 구독 | 채팅, 주식 종목 |
| **사용자별 방** | `user:<id>` 방에 그 사용자의 모든 연결을 넣음 → 한 계정의 여러 탭/기기에 동시 전송 | 알림 |
| **엔티티별 방** | `order:<id>`, `doc:<id>` | 주문 상태 추적, 문서 협업 |
| **와일드카드/토픽** | `stock.*` 같은 패턴 구독 | 브로커 스타일 (MQTT) |

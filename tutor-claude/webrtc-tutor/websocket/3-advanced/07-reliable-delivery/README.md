# 07. 신뢰성 있는 전달 — "끊긴 사이의 메시지는 어디로 갔는가"

> **한 줄 요약**: TCP 는 *연결이 살아 있는 동안*만 전달을 보장합니다. 끊긴 순간의 메시지는 사라집니다. **seq + 재생 버퍼 + resume** 으로 놓침을 막고, **멱등성 키**로 중복 부작용을 막으면 "정확히 한 번의 *효과*"를 얻습니다.

## 1. 문제: TCP 의 신뢰성은 "연결 안"에서만

```
서버 ── msg#11 ─▶ ✕ (클라이언트 와이파이 끊김)  ── msg#12 ─▶ ✕ ──  …
                  │
                  └ TCP 재전송은 "같은 연결"에서만 동작. 연결이 사라지면 서버 커널은 그 데이터를 버린다.
클라이언트가 재연결하면 새로운 TCP 연결 → 서버 입장에선 "처음 보는 클라이언트" → 11, 12 는 영영 도착하지 않는다.
```

채팅 메시지, 주문 체결 알림, 협업 편집 연산이 사라지면 곧 **데이터 불일치**입니다. 앱 레벨의 해법이 필요합니다.

### 전달 보장 수준

| 수준 | 의미 | 구현 | 비고 |
|---|---|---|---|
| at-most-once | 보내고 잊음. 유실 가능, 중복 없음 | 기본 WebSocket | 커서/타이핑 표시처럼 유실 괜찮은 것 |
| **at-least-once** | 유실 없음, **중복 가능** | seq + resume + 재시도 | 이 장의 A 파트 |
| exactly-once *delivery* | 정확히 한 번 전달 | **네트워크에서 불가능** | "ack 가 유실되면?" 의 무한 반복 (두 장군 문제) |
| exactly-once *effect* | 중복 전달돼도 효과는 한 번 | at-least-once + **멱등 처리** | 이 장의 B 파트 |

## 2. A) 이벤트 스트림 resume

### 세 가지 약속
1. **서버가 스트림의 모든 이벤트에 단조 증가 seq 를 붙인다** (`ReplayLog.append`)
2. **서버가 최근 N개를 보관한다** (링 버퍼)
3. **클라이언트는 마지막으로 받은 seq 를 기억**하고, 연결될 때마다 `afterSeq` 를 보내 *그 이후*를 요청한다

```
클라이언트 last=10 ──(끊김)──                              ──(재연결) stream.subscribe {afterSeq:10}
서버 publish #11..#20 (버퍼에 저장)                          ◀── 서버: ReplayLog.since(10) → [#11..#20] 재전송
                                                            ──▶ 그 뒤로는 실시간 #21, #22 …
```

### 응답 모드 3가지
| mode | 상황 | 클라이언트 동작 |
|---|---|---|
| `fresh` | `afterSeq` 없음(최초 구독) | 지금부터 수신 |
| `resumed` | 버퍼에 이어 붙일 구간이 있음 | 재전송분을 순서대로 처리 |
| `gap` | 너무 오래 끊겨 버퍼에서 이미 밀려남 | **스냅샷으로 전체 재동기화** 후 seq 를 서버 최신으로 |

> **버퍼 크기 = 허용할 단절 시간 × 이벤트율.** 초당 100건·5분 허용 → 30,000건. 이를 넘길 만큼 끊기면 gap 으로 "전체 상태 재다운로드"를 하는 설계가 보통입니다(Slack/Discord 도 유사하게 동작).

### 순서가 중요하다: 먼저 방에 들어가고, 그다음 재생
```ts
await ctx.hub.join(ctx.conn, ROOM);   // ① 이후 이벤트는 실시간으로 받기 시작
const r = log.since(afterSeq);        // ② 그 이전 놓친 구간을 버퍼에서
for (const ev of r.items) conn.send(ev);
```
① 과 ② 사이에 발행된 이벤트는 *실시간과 재생 양쪽으로* 올 수 있어 **중복**이 생길 수 있습니다. 그래서 클라이언트가 seq 로 거릅니다.
반대로 ②→① 순서면 그 사이 이벤트를 **놓칠** 수 있습니다. *중복은 걸러낼 수 있지만 누락은 복구할 수 없으므로* 항상 "먼저 구독, 나중에 재생"입니다.

### 클라이언트 판정 (`SeqTracker`)
```
seq === last+1 → 전달(deliver)
seq <= last    → 중복(duplicate): 버림
seq >  last+1  → 건너뜀(gap):    버리고, 재생이 올 때까지 기다림
```
gap 으로 버린 이벤트는 서버가 재생해 주므로 *순서가 뒤바뀌지 않습니다*. (버리지 않고 임시 버퍼에 넣었다가 정렬하는 방식도 있지만, 단순하고 안전한 쪽을 택했습니다.)

## 3. 분산 환경에서의 seq (심화) — 가장 어려운 부분

이 장은 서버 1대입니다. 서버가 여러 대일 때 "스트림의 단일 순서"는 어디서 만들까요?

| 방법 | 설명 | 장단점 |
|---|---|---|
| **스트림 소유 노드 1대** | 스트림(방)마다 담당 노드를 정해(해싱) 그 노드가 seq 를 부여 | 단순, 순서 보장. 노드 장애 시 담당 이전 필요 |
| **Redis `INCR` + Stream** | `XADD` 의 ID 가 곧 순서 있는 seq. `XRANGE`/`XREAD` 로 resume | 영속, 순서, 재생 내장. Redis Streams 가 사실상 정답 |
| **Kafka 파티션 오프셋** | 파티션 오프셋을 seq 로. 컨슈머가 오프셋으로 resume | 대규모·영속·재처리. 지연 증가, 운영 비용 |
| **DB 시퀀스/auto-increment** | 이벤트를 DB 에 저장, id 가 seq | 영속·감사 쉬움. 쓰기 병목 |
| 클라이언트별 큐(inbox) | 사용자마다 메시지함(Redis List/DB). 읽음 위치(cursor)로 복구 | 채팅/알림에 흔함. 팬아웃 저장 비용 |

Redis Pub/Sub 은 **유실이 가능한 at-most-once** 라서, 이 장의 신뢰성을 분산으로 확장하려면 *영속 로그(Streams/Kafka/DB)* 가 필요합니다. (8장에서 Pub/Sub 의 한계를 다시 다룹니다)

## 4. B) 멱등성 키 — "응답이 사라지면 재시도해도 안전한가?"

가장 위험한 순간: 클라이언트가 `order.create` 를 보냈고 **서버는 처리했는데 응답이 유실**되었습니다.
클라이언트는 타임아웃을 받고 *성공/실패를 알 수 없습니다.* 재시도하면? → **주문이 2건**(이중 결제).

```
클라이언트: order.create (key=K) ───▶ 서버: 주문 생성(#1), key=K → 결과 저장
                              ◀─ ✕ 응답 유실
클라이언트: 타임아웃. 재시도 order.create (key=K) ──▶ 서버: key=K 이미 처리됨 → 주문 안 만들고 #1 의 결과를 그대로 반환
```

**규칙**
* **클라이언트가 "시도 단위로" 키를 생성**(UUID). 재시도할 때 **같은 키**를 쓴다. (새 요청이면 새 키)
* 서버는 `키 → 결과` 를 저장하고, 재요청이면 **부수효과를 실행하지 않고 저장된 결과를 반환**한다. 키 저장은 **TTL**(예: 24시간)과 함께.
* **키 저장과 부수효과가 원자적이어야** 합니다. (주문 INSERT 와 키 INSERT 를 한 트랜잭션에, 또는 DB `UNIQUE(idempotency_key)` 제약으로 동시 중복 요청도 방어)
* 같은 키로 **다른 내용**이 오면 거절(422)해서 클라이언트 버그를 알립니다.
* **동시에 같은 키 두 요청**이 오면 하나는 대기하거나 409 를 반환.
* Stripe, 결제 API, 메시지 브로커의 "중복 제거(dedup)"가 모두 이 패턴입니다.

> 읽기 전용/자연 멱등 연산(`PUT /users/1 {…}`, "상태를 X 로 설정")은 키가 필요 없습니다. **증가·추가·생성**류(`+1`, `INSERT`, "결제")가 위험합니다.

## 5. WebSocket 에서 요청 재시도 정책

* **타임아웃 ≠ 실패.** 재시도 전에 이 요청이 **멱등한지** 따져 보세요.
* 재시도에는 **백오프 + 지터 + 최대 횟수**. 모든 클라이언트가 동시에 재시도하면 폭주합니다(4장).
* 연결이 끊긴 사이 `send()` 한 메시지: WsClient 의 오프라인 큐로 보낼 수 있지만, **큐에 있던 메시지가 재연결 후 중복 처리될 수 있으므로** 서버가 멱등해야 합니다.

## 6. 순서(ordering)

* 같은 연결 안에서는 TCP 가 순서를 보장합니다. 서버 핸들러가 `async` 라면 **서버 내부에서 순서가 뒤섞일 수** 있어서, 이 튜토리얼의 `WsServer` 는 연결별로 메시지를 직렬 큐(`conn.queue`)로 처리합니다.
* **다른 연결 간의 순서**는 보장이 없습니다. "모두에게 같은 순서로 보이게" 하려면 *단일 순서 부여자*(스트림 소유 노드 / 로그)가 seq 를 정해야 합니다(3절).
* 협업 편집 같은 곳은 순서 보장 대신 **CRDT/OT** 로 "순서가 달라도 같은 결과"를 만듭니다.

# 학습 가이드 (Learning Guide)

이 문서는 "왜 이 순서로 배우는지", "각 개념이 어디에 쓰이는지"를 설명합니다.
레슨 코드를 보기 전에 한 번, 다 본 뒤에 다시 한 번 읽으면 좋습니다.

---

## TypeScript를 한 문장으로

> **JavaScript에 "타입"이라는 안전벨트를 더한 언어.**
> 코드를 실행하기 전에(= 컴파일 타임에) 타입 실수를 잡아주고,
> 에디터 자동완성과 리팩터링을 강력하게 만들어 준다.

TypeScript 코드는 `tsc`(또는 tsx, esbuild, swc)를 거쳐 **순수 JavaScript로 변환**되어
실행됩니다. **타입 정보는 이 변환 과정에서 전부 사라집니다.** (4단계 18번 레슨의 핵심)

---

## 큰 그림: 4단계의 의미

| 단계 | 질문 | 배우는 것 |
|------|------|-----------|
| 1. Basic | "이 값은 무슨 타입인가?" | 타입을 붙이고 읽는 법 |
| 2. Intermediate | "이 타입을 어떻게 재사용하는가?" | 제네릭, 타입 가드로 추상화 |
| 3. Advanced | "타입으로 타입을 만들 수 있는가?" | 조건부/매핑/템플릿 리터럴 타입 |
| 4. Practical | "실제 프로젝트에서 어떻게 조합하는가?" | 응답 설계, 에러 처리, 검증 |

대부분의 실무 코드는 **1~2단계 + 3단계의 유틸리티 타입** 정도면 충분합니다.
3단계의 타입 레벨 프로그래밍은 "라이브러리를 만들거나 남의 코드를 읽을 때" 필요합니다.

## 개념 지도 (무엇이 무엇으로 이어지는가)

```
리터럴 타입(01) ─┬─→ 유니온(04) ──→ 판별 유니온(10) ──→ 상태 관리 / 이벤트(19)
                 └─→ as const(05) ──→ enum 대체 패턴

interface(03) ───→ 확장(06) ───→ 제네릭 인터페이스(08) ──→ 리포지토리 패턴(19)

제네릭(08) ──┬──→ 유틸리티 타입(11) ──→ 조건부 타입(12) ──→ infer
             ├──→ 매핑된 타입(13) ──→ 키 리매핑 ─┐
             └──→ keyof + T[K]                    ├──→ 템플릿 리터럴 타입(14)
                                                   │
타입 가드(10) ──→ unknown 검증 ──→ 런타임 검증기(18) ──→ 스키마→타입 추론

Result 패턴(17) ←── 판별 유니온(10) + 제네릭(08)
```

## 자주 하는 질문

### Q. 타입을 어디까지 적어야 하나요?

- **적는다**: 함수의 매개변수, 함수의 공개 반환 타입, 빈 값으로 시작하는 변수, 도메인 모델
- **생략한다**: 초기값이 있는 지역 변수, 화살표 함수의 명백한 반환 타입, 배열/객체 리터럴

과하게 적으면 코드가 지저분해지고, 리팩터링 시 두 군데를 고쳐야 합니다.
"추론이 정확한가?"를 기준으로 판단하세요.

### Q. `any` 는 절대 쓰면 안 되나요?

거의 그렇습니다. 대안:
- 타입을 모를 때 → `unknown` + 타입 가드
- 타입이 너무 복잡할 때 → 부분 타입만 정의하고 나머지는 `Record<string, unknown>`
- 진짜 급할 때 → `// @ts-expect-error` 주석 + TODO (최소한 흔적은 남긴다)

### Q. `interface` 와 `type`, 뭘 쓰죠?

팀 컨벤션을 따르되, 정하는 중이라면:
- 객체/클래스 모양, 특히 공개 API → `interface`
- 유니온, 함수 시그니처, 유틸리티성 타입 → `type`
- (06번 레슨 참고)

### Q. 컴파일 에러 메시지가 너무 길어요.

- **맨 아래 줄부터 위로** 읽으세요. 근본 원인이 아래에 있는 경우가 많습니다.
- `Type 'X' is not assignable to type 'Y'` → "X를 Y 자리에 넣으려는데 안 맞다"
- 객체 타입 불일치는 어떤 프로퍼티가 문제인지 끝까지 펼쳐서 보여줍니다.

### Q. `strict` 모드는 꼭 켜야 하나요?

**네.** 특히 `strictNullChecks`. 끄면 `null`/`undefined` 관련 버그를 컴파일러가
못 잡습니다. 새 프로젝트는 무조건 `"strict": true` 로 시작하세요.
이 프로젝트도 켜져 있습니다 (+ `noUncheckedIndexedAccess` 까지).

## 학습 팁

1. **주석을 읽으며 직접 실행하라.** 눈으로만 보면 3일 뒤 잊습니다.
2. **에러를 일부러 내 보라.** 주석 처리된 `// ❌` 줄의 주석을 풀어 어떤 에러가 나는지 확인.
3. **에디터에서 타입에 마우스를 올려라.** TS가 추론한 타입을 그때그때 확인하는 습관.
4. **`exercises/` 를 손으로 풀어라.** 읽기와 쓰기는 다른 능력입니다.
5. **막히면 레슨 파일에서 비슷한 패턴을 찾아 변형하라.**
